# HTTP 핵심 정리

## 1. 네트워크

| 개념 | 핵심 |
|---|---|
| **IP** | 주소를 보고 패킷을 전달. 도착·순서는 보장하지 않음 |
| **TCP** | 연결 상태를 관리하며 수신 확인·재전송·순서 복구 제공 |
| **UDP** | 연결 설정 없이 데이터그램 전송. 자체 재전송·순서 복구 없음 |
| **포트** | 같은 IP의 TCP·UDP 통신 끝점을 구분. HTTP 기본 **80**, HTTPS **443** |
| **DNS** | 도메인 이름에 대응하는 IP 등의 정보 조회 |
| **소켓** | 프로그램이 운영체제의 네트워크 통신 기능을 사용하는 창구 |

- **계층:** HTTP → TCP 또는 QUIC/UDP → IP → 네트워크 인터페이스.
- **TCP 연결:** SYN → SYN+ACK → ACK. 로그인 인증이 아니라 연결 설정.
- **TCP ACK:** 상대 TCP의 수신 확인. 서버 프로그램의 처리 완료는 아님.
- UDP를 사용하는 프로그램도 자체적으로 연결·세션·재전송을 구현할 수 있음.

## 2. URI·URL

- **URI:** 자원을 식별하는 표현.
- **URL:** 위치와 접근 방법으로 식별하는 URI.
- **URN:** 이름으로 식별하는 URI.

`https://example.com:8443/products?q=book#reviews`

| 부분 | 의미 |
|---|---|
| `https` | 스킴: 접근 방식 |
| `example.com` | 호스트: 도메인 또는 IP |
| `8443` | 접속 포트 |
| `/products` | 자원 경로 |
| `q=book` | 쿼리: 검색·필터 등의 조건 |
| `reviews` | 프래그먼트: 문서 내 위치 등. **HTTP 요청에 포함되지 않음** |

## 3. 브라우저 요청 흐름 

**URL 해석 → DNS 조회 → 연결 설정 → HTTP 요청 → 서버 처리 → HTTP 응답 → 화면 처리**

- HTTPS는 보안 협상도 수행. 기존 연결·캐시가 있으면 일부 과정 재사용.
- HTML을 받은 뒤 CSS·JS·이미지 등을 추가 요청할 수 있음.
- HTTP 메시지 하나가 TCP 패킷 하나와 일치하는 것은 아님.

## 4. HTTP 기본 

**HTTP는 클라이언트가 요청하고 서버가 응답하는 규약.** 웹페이지뿐 아니라 JSON·이미지·영상·파일도 전송하며, 서버끼리의 통신에도 사용.

### Stateful과 Stateless

| 구분 | 의미 | 예시 |
|---|---|---|
| **Stateful** | 이전 대화의 맥락을 유지하고 다음 요청 처리 | “아까 선택한 걸 두 개 주문할게.” |
| **Stateless** | 요청 처리에 필요한 맥락을 각 요청에 포함 | “상품 10번을 두 개 주문할게.” |

Stateless는 다른 서버도 요청을 해석하기 쉬워 **서버 교체·수평 확장에 유리**. 단, 서버들이 필요한 데이터와 설정에 일관되게 접근할 수 있어야 함.

- **무상태 ≠ DB 저장 금지:** 회원·상품·주문 같은 업무 데이터는 저장 가능.
- **무상태 ≠ 연결 종료:** 대화 맥락과 TCP 연결 상태는 다른 문제.
- 로그인처럼 상태가 필요한 기능은 쿠키·서버 세션 등으로 상태 관리 가능.

### 비연결성과 지속 연결

요청마다 연결을 새로 만들면 handshake 비용이 반복됨. 페이지 하나도 HTML·CSS·JS·이미지를 받기 위해 여러 요청이 필요하므로 연결 재사용이 유리.

**HTTP/1.1은 보통 지속 연결을 사용해 여러 요청에 같은 TCP 연결을 재사용.** “HTTP는 요청 한 번마다 무조건 연결을 끊는다”로 외우지 않기.

| 버전 | 핵심 |
|---|---|
| HTTP/1.1 | 텍스트 메시지, 연결 재사용 |
| HTTP/2 | TCP 위의 바이너리 프레임·다중 스트림 |
| HTTP/3 | UDP 위의 QUIC 사용. 연결·신뢰성·보안을 QUIC이 제공 |

### HTTP/1.1 메시지 구조

**시작 줄 → 헤더 → 빈 줄 → 본문(있을 때)**

요청 예시:

```http
POST /members HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 12

{"name":"A"}
```

응답 예시:

```http
HTTP/1.1 201 Created
Location: /members/42
Content-Type: application/json
Content-Length: 9

{"id":42}
```

| 항목 | 의미 |
|---|---|
| 요청 시작 줄 | 메서드 + 요청 대상 + 버전 |
| 응답 시작 줄 | 버전 + 상태 코드 + 설명 문구 |
| `Host` | 요청 대상 호스트 |
| `Content-Type` | 본문 형식. 예: `application/json` |
| `Content-Length` | 본문의 **바이트 길이**. 문자 수와 다를 수 있음 |
| `Location` | 생성한 자원 위치나 리다이렉션 대상 등을 안내 |
| 본문 | 실제 처리·전달할 데이터. 요청과 응답 모두 가질 수 있음 |

- 위 응답은 **201로 생성 성공**, **Location으로 새 회원 URI**를 알림.
- 헤더 이름은 대소문자를 구분하지 않으며, 헤더와 본문 사이에 빈 줄이 필요.
- 실제 HTTP/1.1 줄바꿈은 CRLF. 예시 본문 끝에는 추가 개행이 없다고 가정.
- HTTP/2·3도 메서드·상태·헤더의 의미는 사용하지만 위 텍스트 형태 그대로 전송하지는 않음.

## 5. HTTP 메서드

**URI는 대상, 메서드는 요청의 의미.** 같은 `/members/42`를 GET·PATCH·DELETE로 다룰 수 있음.

| 메서드 | 핵심 | 예시 |
|---|---|---|
| **GET** | 자원 조회 | `GET /members/42` |
| **POST** | 제출한 데이터를 대상의 규칙에 따라 처리 | `POST /members` |
| **PUT** | 지정한 자원을 생성·대체 | `PUT /files/report.txt` |
| **PATCH** | 자원 부분 변경 | `PATCH /members/42` |
| **DELETE** | 대상 자원 제거 요청 | `DELETE /members/42` |
| **HEAD** | GET과 대응하되 응답 본문 없음 | 헤더 정보 확인 |
| **OPTIONS** | 대상의 통신 옵션 확인 | 허용 메서드 등 확인 |
| CONNECT / TRACE | 터널 설정 / 메시지 루프백 진단 | 이름과 용도 정도만 기억 |

### GET과 POST

- **GET:** 검색·필터·정렬 조건은 보통 쿼리로 전달. 본문의 일반적인 의미가 정의되지 않아 GET 본문에 의존하는 설계는 피함. 업무상 상태 변경에 사용하지 않음.
- **POST:** 생성 전용이 아님. 회원 등록뿐 아니라 주문·배송 시작 같은 업무 프로세스에도 사용. 본문 형식과 실제 처리 방식은 API가 정의.

### PUT과 PATCH

현재 정보가 `{"name":"A","age":20}`이고 `{"age":30}`을 보낸다면:

| 요청 | API가 전체 대체·명시 필드 변경으로 정의된 경우 |
|---|---|
| **PUT** | 기존 전체 표현을 대체하므로 name이 빠질 수 있음 |
| **PATCH** | age만 변경하고 name은 유지 |

**나이만 바꾸려면 부분 변경 의도를 표현.** PUT에서 누락 필드를 어떻게 처리할지는 API 계약에 따르므로 “보내지 않은 필드는 무조건 유지된다”로 가정하지 않기.

메서드 이름만으로 기능이 생기지는 않으며 서버가 해당 동작을 구현해야 함.

## 6. 메서드의 속성

- **안전성:** 클라이언트가 업무상 상태 변경을 의도하지 않음. 조회 로그 같은 부수 효과는 별개.
- **멱등성:** 같은 요청 반복의 의도한 효과가 한 번과 같음. **응답이 같다는 뜻은 아님.**
- **캐시 가능성:** 응답을 저장·재사용할 수 있는 성질. 실제 사용 여부는 정책·조건에 따름.

| 메서드 | 안전 | 멱등 |
|---|---|---|
| GET·HEAD·OPTIONS | O | O |
| POST | X | 보장하지 않음 |
| PUT·DELETE | X | O |
| PATCH | X | 보장하지 않음. 변경 내용에 따라 가능 |

### 멱등성은 재시도 판단에 중요

- **PUT:** “가격을 50000으로 설정”은 반복해도 같은 설정 효과.
- **DELETE:** 두 번째 응답이 “이미 없음”이어도 대상이 제거된 효과는 같음.
- **POST:** 첫 주문은 생성됐지만 응답만 유실됐을 수 있음. 다시 실행하면 중복 주문 위험.
- **PATCH:** “나이를 30으로 설정”은 멱등적으로 설계 가능하지만 “재고 1 증가”는 반복 효과가 다름.

POST의 중복 위험은 **서버가 새 URI를 결정해서가 아니라, 같은 처리 작업이 다시 실행될 수 있어서** 발생. 안전한 재시도에는 API의 중복 방지·결과 확인 정책 등이 필요.

캐시는 GET·HEAD가 대표 대상. POST·PATCH도 조건부 가능하지만 일반적인 사용·지원은 제한적. **GET이라고 응답이 무조건 캐시되는 것은 아님.**

## 7. 데이터 전송 

| 상황 | 대표 방식 |
|---|---|
| 정적 파일 조회 | `GET /images/logo.png` |
| 검색·필터·정렬 | `GET /members?name=A` |
| 일반 폼 제출 | POST 본문, `application/x-www-form-urlencoded` |
| 파일과 폼 값 전송 | `multipart/form-data` |
| 구조화된 API 데이터 | JSON 등의 본문, `application/json` |

### 전송 형식의 차이

- **쿼리:** URL의 `?` 뒤에 조건 포함. 조회 조건 전달에 주로 사용.
- **폼 인코딩:** `name=A&age=20`처럼 입력값을 직렬화. POST 폼이면 본문, GET 폼이면 쿼리로 전달.
- **multipart:** boundary로 본문을 여러 파트로 나눠 파일과 입력값을 함께 전달.
- **JSON:** 객체·배열 같은 구조로 데이터 표현. 서버·서버, 앱·서버, 브라우저 스크립트·서버 통신 등에 사용.

**메서드와 본문 형식은 별개.** POST라고 항상 JSON인 것은 아니며, JSON도 HTTP가 강제하는 유일한 형식은 아님.

기본 HTML 폼 제출은 **GET·POST**. 다른 메서드는 스크립트 등의 별도 처리 필요. URL 인코딩은 암호화가 아님.

## 8. URI 설계 
| 개념 | 핵심 | 예시 |
|---|---|---|
| **Document** | 개별 자원 | `/members/42` |
| **Collection** | 서버가 개별 자원 URI를 결정·관리하는 묶음 | `/members` |
| **Store** | 클라이언트가 대상 URI를 지정하는 저장소 | `/files` |
| **Controller** | 추가 프로세스를 실행하는 컨트롤 URI | `/orders/42/start-delivery` |

### 컬렉션과 스토어의 차이

- **컬렉션:** `POST /members` → 서버가 새 회원을 생성하고 `/members/42` 같은 URI 결정.
- **스토어:** `PUT /files/report.txt` → 클라이언트가 지정한 URI에 파일을 생성·대체.

구분 기준은 **개별 자원의 URI를 누가 지정하는가**. 스토어라고 파일이 클라이언트 PC에만 저장된다는 뜻은 아님.

### HTML 폼과 컨트롤 URI

| 방식 | 회원 삭제 요청 예시 |
|---|---|
| 일반 HTTP API | `DELETE /members/42` |
| 기본 HTML 폼 | `POST /members/42/delete` |

기본 폼은 DELETE를 직접 보내지 못하므로 POST와 동작형 경로로 처리할 수 있음. **GET으로 삭제하지 않기.** 자원 중심 설계를 우선하되, 프로세스 실행·폼 제약 등에 필요한 컨트롤 URI도 사용 가능.
