# 6. HTTP 상태 코드

> 출발 질문: 서버와 통신은 성공했지만 주문은 실패했다면 어떤 응답을 해야 할까?

## 6.1 상태 코드는 처리 결과의 공통 표현이다

상태 코드는 응답의 의미를 클라이언트·프록시·도구가 공통으로 해석하게 한다. 본문에 `"success":false`를 넣는 것만으로 HTTP 상태 코드의 역할을 대신할 수는 없다.

| 범위 | 분류 | 읽는 방법 |
|---|---|---|
| 1xx | 정보성 | 최종 응답 전의 처리 정보 |
| 2xx | 성공 | 요청이 성공적으로 수신·처리됨 |
| 3xx | 리다이렉션 등 | 다른 위치 사용이나 저장된 표현 활용 등에 관한 응답 |
| 4xx | 클라이언트 오류 | 요청·인증·권한·현재 조건 등의 문제 |
| 5xx | 서버 오류 | 서버 측에서 요청을 수행하지 못함 |

4xx는 개발자가 사용자를 비난하는 분류가 아니다. 클라이언트가 어떤 조건을 고쳐야 하는지 전달하는 의미다. 알 수 없는 코드는 첫 자리의 분류도 참고하되, 특정 코드를 임의로 성공 취급하지 않는다.

## 6.2 주요 성공 응답

| 코드 | 의미 | 선택 예시 |
|---|---|---|
| 200 OK | 성공 | 상품 조회·처리 결과 응답 |
| 201 Created | 자원 생성 | 주문을 생성하고 새 URI 전달 |
| 202 Accepted | 처리 요청 수락 | 비동기 작업 접수. 완료를 보장하는 코드가 아님 |
| 204 No Content | 성공, 응답 콘텐츠 없음 | 삭제 성공 후 본문 불필요 |
| 206 Partial Content | 범위 요청에 대한 부분 응답 | 파일의 일부 바이트 전송 |

```http
HTTP/1.1 201 Created
Location: /orders/123
Content-Type: application/json

{"id":123,"status":"created"}
```

Location은 생성된 자원의 위치를 알리는 데도 사용된다. Location이 있다고 모든 응답이 리다이렉션은 아니다. **204에는 JSON 본문을 넣지 않는다.**

## 6.3 리다이렉션과 메서드 유지

```text
클라이언트 → GET /old
서버       → 301 + Location: /new
클라이언트 → GET /new
```

리다이렉션을 따르는 클라이언트는 Location을 해석해 새 요청을 보낸다. 서버가 기존 TCP 요청을 물리적으로 다른 서버에 옮겨 꽂는 것이 아니다.

| 코드 | 주요 의미 | 메서드 처리 |
|---|---|---|
| 301 | 영구 이동 | POST를 GET으로 바꾸는 동작이 허용됨 |
| 302 | 일시적 다른 위치 | POST를 GET으로 바꾸는 동작이 허용됨 |
| 303 | 결과를 다른 자원에서 조회 | 보통 GET, HEAD라면 HEAD로 조회 |
| 307 | 일시적 리다이렉션 | 자동으로 따를 때 메서드를 변경하지 않음 |
| 308 | 영구 리다이렉션 | 자동으로 따를 때 메서드를 변경하지 않음 |

메서드·본문 유지가 중요하면 301·302의 관행에 기대지 말고 의도를 명확하게 한다. 클라이언트가 리다이렉션을 자동으로 따르지 않을 수도 있다.

### POST → Redirect → GET, PRG

```text
폼 POST /orders
     ↓ 주문 생성
303 Location: /orders/123
     ↓
GET /orders/123
     ↓
완료 화면에서 새로고침 → GET 재요청
```

완료 화면 새로고침이 원래 POST를 반복하는 문제를 줄인다. 그러나 빠른 중복 클릭·네트워크 재시도까지 막는 완전한 중복 주문 방지책은 아니다.

### 304 Not Modified

304는 캐시 검증에서 사용한다. 조건부 GET·HEAD에서 저장된 표현이 여전히 유효할 때 반환한다. **새 페이지로 이동하라는 뜻이 아니며 응답 본문을 보내지 않는다.** 브라우저는 캐시에 있는 데이터를 재사용한다.

근거: [MDN 리다이렉션](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections), [RFC 9110 상태 코드](https://www.rfc-editor.org/rfc/rfc9110.html#section-15).

## 6.4 주요 4xx 응답

| 코드 | 판단 기준 | 예시 |
|---|---|---|
| 400 Bad Request | 요청 문법·구성 등이 잘못됨 | JSON 파싱 실패 |
| 401 Unauthorized | 유효한 인증 자격이 필요함 | 로그인 정보 없음·만료 |
| 403 Forbidden | 요청을 이해했지만 수행 거절 | 다른 사용자 주문 접근 금지 |
| 404 Not Found | 대상 없음 또는 존재를 공개하지 않음 | 없는 상품 ID |
| 405 Method Not Allowed | 해당 대상에서 메서드 불허 | 조회 전용 대상에 DELETE |
| 409 Conflict | 현재 자원 상태와 충돌 | 이미 취소된 주문의 처리 충돌 |
| 412 Precondition Failed | 요청의 전제 조건 실패 | If-Match 버전 불일치 |
| 415 Unsupported Media Type | 본문 형식 등을 지원하지 않음 | JSON만 받는데 다른 형식 제출 |
| 422 Unprocessable Content | 형식은 이해했으나 내용 처리 불가 | 계약상 허용하지 않는 값 |
| 429 Too Many Requests | 요청 빈도 제한 | 짧은 시간 내 과도한 요청 |

400과 422 등은 API의 오류 정책을 일관되게 정해야 한다. 401에는 HTTP 인증 규칙에 맞는 WWW-Authenticate 챌린지가 요구된다. 405에는 허용 메서드를 나타내는 Allow가 필요하다.

‘인증됨’과 ‘권한 있음’은 다르다. 로그인한 사용자도 타인의 데이터에 접근할 권한은 없을 수 있다.

## 6.5 주요 5xx 응답

| 코드 | 의미 |
|---|---|
| 500 Internal Server Error | 예상하지 못한 서버 내부 실패 |
| 502 Bad Gateway | 게이트웨이·프록시가 상위 서버에서 유효하지 않은 응답을 받음 |
| 503 Service Unavailable | 일시적인 과부하·점검 등으로 서비스 제공 불가 |
| 504 Gateway Timeout | 게이트웨이·프록시가 필요한 상위 응답을 제때 받지 못함 |

클라이언트 입력 오류를 모두 500으로 처리하면 원인과 대응을 판단하기 어렵다. 반대로 5xx라고 무조건 즉시 재시도하지도 않는다. 메서드의 멱등성, Retry-After, 지수적 대기 등을 함께 고려한다.

## 6.6 오류 본문은 행동할 수 있게 만든다

```json
{
  "code": "INVALID_QUANTITY",
  "message": "수량은 1 이상이어야 합니다.",
  "field": "quantity"
}
```

위 필드명은 예시 API의 계약이지 HTTP의 필수 규격이 아니다. 상태 코드는 공통 분류를, 오류 본문은 업무상 이유와 필요한 행동을 전달한다. 내부 스택 추적이나 비밀 값을 그대로 공개하지 않는다.

상태 코드 참고: [MDN 상태 코드 목록](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status).
