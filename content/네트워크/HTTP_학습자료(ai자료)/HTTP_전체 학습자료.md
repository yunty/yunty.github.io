## 먼저 보는 전체 지도

```text
사용자 내부망                  통신사 망                     서비스 망
PC → 공유기 → ONT → 광분배기 → OLT → 집선망·가입자 관리 → 백본 → 목적지 서버
 │                                                                    │
 └──────────────────── HTTP 요청과 응답 ────────────────────────────────┘
```

위의 ONT·광분배기·OLT는 FTTH·PON의 한 예다. 다른 가입자망에서는 장비가 달라진다. **HTTP는 이 경로 자체를 만드는 규약이 아니라, 그 경로를 통해 프로그램끼리 주고받는 요청·응답의 규약**이다.

```text
애플리케이션: HTTP / API / 웹 로그인 상태
보안:         TLS — HTTPS 통신 보호
전송:         TCP 또는 QUIC — QUIC은 UDP 위에서 동작
네트워크:     IP — 목적지 네트워크로 전달
링크·물리:    이더넷·Wi-Fi·광회선 등
```

## 예시를 읽는 규칙

- 도메인은 `example.com`, 외부 IP는 문서용 주소를 사용한다. 실제로 접속할 서비스가 아니다.
- 직접 실행할 실습 주소는 `http://127.0.0.1:8765`다.
- HTTP 텍스트 예시는 특별한 표시가 없으면 HTTP/1.1 형식이다. 설명용 예시에서는 일부 헤더를 생략한다. 실제 메시지의 길이·경계는 HTTP 라이브러리가 올바르게 처리해야 한다.
- `HTTP 요청 하나 = TCP 패킷 하나`는 아니다. 요청이 여러 조각으로 전송되거나 한 연결에서 여러 요청이 처리될 수 있다.
- 웹의 ‘세션’과 TCP의 ‘연결 상태’는 다른 개념이다. 두 개를 항상 구분한다.

# 1. 인터넷 네트워크

> 출발 질문: 웹서버의 IP를 알면 통신에 필요한 정보가 모두 준비된 것일까?

## 1.1 프로그램끼리 통신한다

‘내 PC가 서버에 접속한다’는 말은 더 정확히는 **내 PC에서 실행 중인 프로그램이 상대 장비에서 실행 중인 프로그램과 데이터를 주고받는다**는 뜻이다.

```text
브라우저 → 운영체제 → 네트워크 → 상대 운영체제 → 웹서버 프로그램
```

컴퓨터 한 대에서 여러 프로그램이 동시에 통신할 수 있다. 따라서 장비 쪽으로 가는 주소와 그 안에서 사용할 통신 끝점을 구분해야 한다.

| 요소 | 구분하는 것 | 예시 |
|---|---|---|
| IP 주소 | IP 네트워크에서 사용하는 주소 | `203.0.113.10` |
| 포트 | TCP·UDP 통신의 끝점 | TCP `443` |
| 도메인 | 사람이 사용하는 이름 | `example.com` |
| MAC | 현재 이더넷 구간에서 프레임을 전달할 주소 | 다음 홉 장비의 MAC |

‘IP는 컴퓨터, 포트는 프로그램’이라는 설명은 입문용 요약이다. 실제로는 장비에 주소가 여러 개일 수 있고, 하나의 서비스 포트를 여러 프로세스가 공유하는 구성도 가능하다.

## 1.2 IP의 역할과 한계

IP는 출발지·목적지 주소 등을 담아 패킷을 전달한다. 라우터들은 목적지와 라우팅 정보를 보고 다음 경로를 선택한다.

```text
[출발지 IP | 목적지 IP | 상위 계층 데이터]
       → 라우터 → 라우터 → 목적지
```

IP만으로는 도착·순서·중복 제거가 보장되지 않는다. 경로에서 버려지거나, 순서가 달라지거나, 통신 자체가 실패할 수 있다. 상위 프로토콜은 필요한 수준의 전송 관리를 추가한다.

L2 스위치는 일반적인 이더넷 전달에서 목적지 MAC을 보고, L3 라우터는 IP 경로를 선택한다. 다른 네트워크로 보내는 PC는 최종 서버 IP와 함께 **현재 넘겨줄 게이트웨이의 MAC**을 사용한다. IPv4에서 같은 링크의 IP에 대응하는 MAC을 찾는 대표적인 절차가 ARP다.

## 1.3 TCP는 연결별 진행 기록을 관리한다

TCP는 애플리케이션에 **신뢰성 있는 순서대로의 바이트 흐름**을 제공한다. 무한정 성공을 보장하는 것은 아니며, 복구할 수 없으면 연결 오류로 끝날 수 있다.

```text
클라이언트                         서버
    ├─ SYN, SEQ=1000 ─────────────→│
    │← SYN+ACK, SEQ=7000, ACK=1001 ┤
    ├─ ACK, SEQ=1001, ACK=7001 ───→│
    │          연결 설정           │
```

Handshake는 연결 설정과 초기 정보 교환이다. **로그인이나 상대 신원을 인증하는 과정은 아니다.** TLS의 인증과 별개다.

연결 후 클라이언트가 100바이트를 보낸다면:

```text
클라이언트                         서버
    ├─ SEQ=1001, 데이터 100바이트 →│  1001~1100 수신
    │← ACK=1101 ───────────────────┤  다음은 1101을 기대
```

ACK 번호는 ‘다음에 기대하는 순서 번호’다. ACK=1101은 그 앞의 연속된 데이터를 받았다는 뜻이다. TCP ACK는 **상대 TCP가 받은 것**을 의미한다. 서버 프로그램의 주문 저장·결제 완료를 보증하지 않는다.

### TCP 세션은 어디에 있는가?

보통 TCP 세션이라고 부르는 것은 TCP 연결이다. **중앙에 상태가 하나 존재하는 것이 아니라 양 끝이 각각 연결 상태를 유지**한다.

```text
클라이언트의 연결 기록              서버의 연결 기록
내 IP·포트 / 상대 IP·포트           내 IP·포트 / 상대 IP·포트
다음 송신 번호                     다음 송신 번호
미확인 송신 범위                   미확인 송신 범위
다음 수신 기대 번호                다음 수신 기대 번호
버퍼·윈도·타이머·연결 단계          버퍼·윈도·타이머·연결 단계
          ↕ 필요한 헤더와 데이터 교환 ↕
```

프로그램은 소켓이라는 운영체제 인터페이스를 통해 읽고 쓴다. 연결 관리 기록은 소켓에 연관된 내부 자료구조 등으로 관리된다. 세션 정보 전체를 매번 상대에게 보내는 것은 아니다.

### 손실·순서·속도 관리

- **재전송:** 확인되지 않은 전송을 타이머나 손실 징후에 따라 다시 보낸다.
- **순서 관리:** 바뀐 순서로 도착해도 연속된 바이트 흐름으로 제공한다.
- **흐름 제어:** 상대 수신 버퍼가 감당할 수 있는 범위를 고려한다.
- **혼잡 제어:** 네트워크 혼잡을 고려해 전송량을 조절한다.

통신이 없을 때는 상태를 보관하고 대기할 수 있다. 상대가 갑자기 꺼져도 즉시 모를 수 있다. 생존 확인이 필요하면 TCP Keepalive나 애플리케이션의 Heartbeat 등을 사용한다.

### 종료

한쪽의 FIN은 ‘이 방향으로 더 보낼 데이터가 없다’는 뜻이다. 반대 방향의 전송은 남아 있을 수 있다. 정상 종료에는 FIN·ACK 교환 등이 사용되며, TIME_WAIT 같은 중간 상태를 거칠 수 있다. 오류나 강제 중단에는 RST가 사용될 수 있다.

근거: [TCP 표준 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html).

## 1.4 UDP는 데이터그램 단위로 보낸다

UDP 자체는 TCP와 같은 연결 설정·재전송·순서 복구를 제공하지 않는다. 수신 프로그램은 데이터그램 단위로 받는다.

| 구분 | TCP | UDP |
|---|---|---|
| 애플리케이션에 보이는 단위 | 바이트 흐름 | 데이터그램 |
| 기본 연결 설정 | 있음 | TCP와 같은 절차 없음 |
| 신뢰성·순서 복구 | 프로토콜이 제공 | UDP 자체는 제공하지 않음 |
| 상위 프로그램의 상태 유지 | 가능 | 가능 |

UDP가 단순하다고 모든 상황에서 무조건 빠른 것은 아니다. 필요한 기능을 애플리케이션이 추가하면 비용도 생긴다. HTTP/3의 QUIC처럼 UDP 위에 연결·재전송·보안·혼잡 제어를 구현할 수 있다.

근거: [UDP 표준 RFC 768](https://www.rfc-editor.org/rfc/rfc768.html), [QUIC 표준 RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html).

## 1.5 포트와 연결 구분

```text
브라우저의 끝점                     서버의 끝점
192.168.1.10:51000      ↔      203.0.113.10:443
192.168.1.10:51001      ↔      203.0.113.10:443
```

같은 서버 포트를 사용해도 클라이언트 쪽 포트 등이 달라 두 TCP 연결을 구분한다. 서버는 포트 443에서 많은 연결을 동시에 처리할 수 있다. NAT가 중간에 있으면 구간에 따라 관찰되는 주소·포트가 달라질 수 있다.

## 1.6 DNS는 이름에 관한 정보를 찾는다

DNS는 이름을 IP 등의 정보로 조회하는 분산 시스템이다. IP로 가는 실제 패킷 경로를 고르는 장비는 DNS가 아니라 라우터다.

```text
브라우저·운영체제 캐시 확인
          ↓ 필요하면
재귀 DNS 리졸버에 문의
          ↓ 리졸버 캐시에도 없다면
루트 → 최상위 도메인 → 권한 DNS 서버 등을 따라 조회
          ↓
결과를 받아 일정 조건·시간 동안 캐시
```

대표 레코드는 IPv4용 A, IPv6용 AAAA, 다른 이름을 가리키는 CNAME이다. 한 도메인이 여러 IP를 반환하거나 한 IP에 여러 사이트가 연결될 수 있다. DNS는 흔히 UDP를 쓰지만 TCP나 암호화된 전송 방식도 사용한다.

근거: [DNS 개념 RFC 1034](https://www.rfc-editor.org/rfc/rfc1034.html).

# 2. URI와 브라우저 요청 흐름

> 출발 질문: 주소창에 도메인을 쓰는 것과 HTTP 요청에 경로를 쓰는 것은 어떻게 연결될까?

## 2.1 URI와 URL

**URI는 자원을 식별하는 표현**이고, **URL은 위치·접근 방법을 이용하는 식별 방식**이다. 웹에서 사용하는 `https://example.com/products/10` 같은 주소는 URL이면서 URI다.

입문 단계에서는 ‘URL이 URI에 포함된다’고 이해하되, URI를 단순히 ‘IP로 바꿀 문자열’로 생각하지 않는다. 요청의 경로·쿼리 등도 대상 자원을 식별하는 데 사용된다.

## 2.2 URL 분해

```text
https://example.com:443/products/10?color=black#reviews

https         스킴 — 어떤 방식으로 접근하는가
example.com   호스트 — 접속 대상 이름
443           포트 — 접속 끝점, HTTPS 기본값은 보통 생략
/products/10  경로 — 대상 자원
color=black   쿼리 — 추가 선택·검색 조건 등
reviews       프래그먼트 — 문서 내 위치 등 클라이언트 측 식별
```

**`#reviews`는 일반적인 HTTP 요청 대상에 포함되어 서버로 전송되지 않는다.** 브라우저가 해당 부분을 이용해 화면을 이동할 수 있다. 반면 쿼리는 서버 요청에 포함된다.

```http
GET /products/10?color=black HTTP/1.1
Host: example.com

```

공백이나 한글처럼 상황에 따라 그대로 쓸 수 없는 문자는 적절히 인코딩한다. 퍼센트 인코딩은 **문자열 표현을 위한 변환이지 암호화가 아니다.** 비밀번호를 URL에 넣어도 숨겨지지 않는다.

경로와 쿼리에 이름·값을 어떤 의미로 배치할지는 API 설계의 영역이다. URL의 문법만으로 ‘이 파라미터는 상품 색상’이라는 업무 의미가 정해지는 것은 아니다.

근거: [URI 문법 RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.html).

## 2.3 브라우저에서 서버까지

캐시나 기존 연결이 없는 단순한 HTTPS·HTTP/1.1 예시다.

```text
① URL 해석
   호스트·포트·경로·쿼리를 구분
             ↓
② DNS 조회
   호스트 이름에 대응하는 IP 확인
             ↓
③ TCP 연결
   상대 IP·포트로 연결 설정
             ↓
④ TLS 협상
   인증서 검증, 암호화 통신에 필요한 정보 교환
             ↓
⑤ HTTP 요청
   GET /products/10 ... 전송
             ↓
⑥ 서버 처리
   경로 선택, 권한 확인, DB 조회 등
             ↓
⑦ HTTP 응답
   상태 코드·헤더·본문 수신
             ↓
⑧ 화면 처리
   HTML 해석, CSS·JS·이미지 추가 요청, 렌더링
```

각 단계가 항상 새로 수행되지는 않는다. DNS 결과·응답 캐시를 재사용하거나, 이미 설정된 연결을 사용할 수 있다. HTTP/3는 TCP 대신 QUIC을 사용하고 TLS 협상도 QUIC에 통합된다.

TLS는 통신 내용의 암호화·무결성과 인증서에 기반한 서버 인증 등을 제공한다. TCP handshake와 TLS handshake는 역할이 다르다. [TLS 1.3 표준](https://www.rfc-editor.org/rfc/rfc8446.html).

## 2.4 계층별로 무엇을 보는가?

| 처리 주체 | 주로 보는 정보 | 하는 일 |
|---|---|---|
| DNS 리졸버 | 도메인 이름 | 주소 등의 정보 조회 |
| L2 스위치 | VLAN·목적지 MAC | 링크 안에서 프레임 전달 |
| 라우터 | 목적지 IP·경로 정보 | 다음 네트워크로 전달 |
| TCP 처리 | 포트·연결 상태·SEQ·ACK | 바이트 흐름 전달 |
| HTTP 처리 | 메서드·호스트·경로·헤더·본문 | 요청 해석·응답 생성 |

HTTPS의 HTTP 내용은 암호화되어 전달된다. 따라서 일반적인 중간 라우터가 `/products/10`을 읽고 상품 요청을 처리하는 것은 아니다. TLS를 종료하는 프록시 등은 HTTP를 처리할 수 있다.

## 2.5 도메인 하나와 서버 한 대는 같은 뜻이 아니다

```text
example.com
    ↓ DNS 등으로 접속 거점 선택
로드밸런서·리버스 프록시
    ├─ 애플리케이션 서버 A
    └─ 애플리케이션 서버 B
```

반대로 한 IP에서 여러 도메인의 웹서비스를 제공할 수도 있다. HTTP/1.1의 Host, HTTP/2·3의 `:authority`, TLS의 서버 이름 관련 정보 등이 사이트 선택에 사용된다.

서버가 보내 준 HTML에는 다른 이미지·CSS·스크립트의 주소가 포함될 수 있다. **페이지 하나를 열어도 HTTP 요청은 여러 개** 발생할 수 있다.

관련 설명: [MDN HTTP 시스템 개요](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview).

# 3. HTTP 기본과 메시지

> 출발 질문: HTTP가 무상태라면 서버는 데이터를 저장하지 못하는 것일까?

## 3.1 HTTP의 위치

HTTP는 자원에 대한 요청과 응답의 의미를 정하는 애플리케이션 프로토콜이다. HTML뿐 아니라 이미지·JSON·파일 등을 전달할 수 있다. 브라우저와 서버 사이뿐 아니라 앱·서버, 서버·서버 사이에서도 사용한다.

```text
클라이언트                         서버
요청을 생성 ── 메서드·대상·데이터 ─→ 요청 해석·처리
응답을 사용 ←─ 상태·헤더·데이터 ─── 응답 생성
```

클라이언트·서버는 역할이다. 서버가 다른 서비스에 요청하면 그 통신에서는 클라이언트가 된다. [HTTP 의미 체계 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).

## 3.2 Stateful과 Stateless

Stateful은 이전 대화의 상태를 유지하며 다음 처리를 이어 가는 방식이다. Stateless에서는 각 요청을 처리하는 데 필요한 정보를 요청 자체에서 얻을 수 있도록 구성한다.

```text
대화 상태에 의존하는 예
요청 1: “상품 A를 선택할게.”
요청 2: “그걸 두 개 살게.” → 이전 선택을 알아야 해석 가능

독립적으로 해석하는 예
요청: “사용자 42의 권한으로 상품 A를 두 개 주문할게.”
```

HTTP는 이전 요청과의 관계를 프로토콜 자체가 자동으로 유지하지 않는다. 그러나 애플리케이션은 쿠키·서버 세션 등으로 상태를 추가할 수 있다.

**무상태는 DB에 회원·상품·주문을 저장하지 말라는 뜻이 아니다.** 서버의 자원 상태와 클라이언트와의 대화 상태를 구분한다. 또한 JWT를 사용하거나 로그인 기능이 없다고 자동으로 REST 설계를 만족하는 것은 아니다.

### 세 가지 상태를 분리해서 보기

| 상태 | 예시 | 일반적인 관리 위치 |
|---|---|---|
| TCP 연결 상태 | 어디까지 송수신했는가 | 양 끝 운영체제 |
| 웹 로그인 세션 | 어떤 사용자로 로그인했는가 | 애플리케이션의 세션 저장소 등 |
| 업무 데이터 | 어떤 주문이 생성되었는가 | DB 등 |

TCP 연결이 종료되어도 로그인 세션이나 주문 기록은 남을 수 있다. [MDN HTTP의 무상태성과 쿠키](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Overview#http_is_stateless_but_not_sessionless).

## 3.3 ‘비연결성’이라는 설명을 읽을 때

HTTP 입문에서 비연결성을 ‘응답 후 연결 종료’로 설명하기도 한다. 하지만 **현대 HTTP가 요청마다 반드시 연결을 닫는다는 뜻으로 외우면 틀린다.**

- HTTP/1.1은 보통 지속 연결을 사용해 여러 요청·응답에 TCP 연결을 재사용한다.
- HTTP/2는 한 연결에서 여러 스트림을 통해 요청을 함께 처리한다.
- HTTP/3는 QUIC 연결 위에서 스트림을 사용한다.

HTTP의 무상태성과 전송 연결의 유지 여부는 별개다. 연결을 재사용하면 연결 설정 비용을 줄일 수 있다. 연결에 기대지 않고 로그인 식별을 설계하는 이유는 새 연결에서도 사용자를 알아야 하기 때문이다.

## 3.4 HTTP/1.1 메시지의 기본 모양

```text
시작 줄
헤더 이름: 값
헤더 이름: 값
빈 줄
본문 — 있을 때
```

요청의 예:

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 12

{"name":"A"}
```

| 부분 | 의미 |
|---|---|
| POST | 요청 작업의 의미를 나타내는 메서드 |
| /users | 요청 대상 |
| HTTP/1.1 | 메시지 버전 |
| Host | 요청한 호스트와 필요하면 포트 |
| Content-Type | 본문 표현의 형식 |
| Content-Length | 여기서는 본문의 바이트 길이 |
| 빈 줄 | 헤더 영역의 끝 |
| JSON 본문 | 처리할 실제 데이터 |

응답의 예:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 11

{"ok":true}
```

응답 시작 줄에는 상태 코드가 들어간다. `OK` 같은 설명 문구보다 **숫자 코드의 의미**가 중요하다. 헤더 이름은 대소문자를 구분하지 않지만 값의 해석 규칙은 헤더마다 다르다.

실제 HTTP/1.1 줄바꿈은 CRLF다. 헤더 뒤의 CRLF가 두 번 이어지는 부분이 헤더와 본문을 구분한다. 예시의 12·11은 ASCII 본문의 길이이며 끝에 추가 개행이 없다고 가정한다. 한글은 문자 수와 UTF-8 바이트 수가 다를 수 있다.

## 3.5 HTTP 메시지 경계와 TCP 경계는 다르다

TCP는 바이트 흐름이다. 프로그램이 한 번 쓴 데이터가 상대 프로그램의 한 번 읽기에 그대로 대응하지 않는다.

```text
전송하려는 HTTP 요청: [시작 줄 + 헤더 + 본문]
실제 수신:           [시작 줄 일부] [나머지 헤더] [본문 일부] [본문 나머지]
```

수신 측 HTTP 구현은 규칙에 따라 메시지를 구분한다. HTTP/1.1에서는 상태·메서드에 따른 본문 유무, Content-Length, chunked 전송, 일부 응답의 연결 종료 등이 경계 결정에 사용된다. chunked일 때 Content-Length를 함께 보내는 식으로 임의 조합하지 않는다.

프레임워크를 쓸 때는 이런 세부 처리를 HTTP 라이브러리에 맡긴다. HTTP/2·3에서는 프레임 기반의 다른 경계 규칙을 사용한다.

근거: [HTTP/1.1 구문·메시지 경계 RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html), [MDN HTTP 메시지](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages).

## 3.6 HTTPS와 버전의 관계

HTTPS는 HTTP 의미에 보안 전송을 적용한 것이다. TLS는 암호화·무결성·서버 인증 등을 제공한다. HTTPS라고 서비스의 모든 데이터 취급이나 업무 처리가 안전하다는 뜻은 아니다.

| 버전 | 핵심 특징 |
|---|---|
| HTTP/1.1 | 텍스트 메시지, 연결 재사용 가능 |
| HTTP/2 | 바이너리 프레임, TCP 연결 위의 여러 스트림 |
| HTTP/3 | QUIC 스트림 사용, QUIC은 UDP 위에서 동작하며 TLS 통합 |

### HTTP/3가 UDP를 사용하는 이유

TCP는 하나의 순서 있는 바이트 흐름이므로 손실 복구 때문에 다른 HTTP/2 스트림의 데이터 전달도 대기할 수 있다. QUIC은 각 스트림의 순서를 독립적으로 관리해 이 전송 계층의 대기를 줄인다. 연결 설정 지연과 경로 변경 대응도 개선하도록 설계됐다.

**HTTP/3가 UDP를 쓴다고 신뢰성이나 연결을 포기한 것은 아니다.** QUIC이 연결 상태·수신 확인·손실 복구·혼잡 제어를 제공한다. 스트림들이 연결의 혼잡 제어를 공유하므로 서로의 성능에 완전히 무관한 것도 아니다.

근거: [HTTP/3 RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html), [QUIC RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html).

# 4. HTTP 메서드

> 출발 질문: 주소가 `/products/10`으로 같아도 조회와 삭제를 구분할 수 있을까?

## 4.1 대상과 동작을 나눈다

상품 10번이라는 대상은 URI로 식별하고, 요청의 의미는 메서드로 표현할 수 있다.

```text
GET    /products/10 → 상품 표현 조회
PATCH  /products/10 → 일부 변경 요청
DELETE /products/10 → 대상 삭제 요청
```

메서드가 서버 기능을 자동 생성하지는 않는다. 서버 프로그램이 그 조합을 해석하고 처리해야 한다. `GET /delete-product`로 삭제를 구현할 수는 있지만, 조회 메서드의 의미와 충돌하는 설계다.

## 4.2 메서드별 의미

| 메서드 | 핵심 의미 | 대표 사례 |
|---|---|---|
| GET | 대상 자원의 표현 조회 | 목록·상세 조회 |
| HEAD | GET과 대응하되 응답 본문 없이 메타데이터 확인 | 자원 정보·변경 여부 확인 |
| POST | 대상 자원이 요청 내용을 자신의 규칙으로 처리 | 주문 생성·업로드·작업 실행 |
| PUT | 지정 URI의 상태를 보낸 표현으로 생성·대체 | 클라이언트가 지정한 파일 경로 저장 |
| PATCH | 대상에 부분 변경 적용 | 상품 가격 변경 |
| DELETE | 대상 URI와 현재 기능·표현의 연결 제거 요청 | 상품 삭제 API |
| OPTIONS | 대상에 가능한 통신 옵션 조회 | CORS 사전 요청 등 |

### GET

검색 조건은 보통 쿼리에 넣는다.

```http
GET /products?category=book&page=1 HTTP/1.1
Host: example.com

```

GET 본문은 일반적인 의미가 정의되어 있지 않고 구현 간 호환 문제가 있다. 조회 조건을 본문에 넣는 것을 기본 설계로 삼지 않는다.

### POST

‘생성만 하는 메서드’보다 넓다. 제출된 데이터를 처리하는 의미이므로 생성·명령 실행 등에 사용한다. 서버가 새 자원의 URI를 정하는 컬렉션 생성에서는 `201 Created`와 Location을 사용할 수 있다.

### PUT과 PATCH

```text
현재: {"name":"키보드", "price":50000}

PUT   → 계약에서 정한 전체 대체용 표현을 보냄
PATCH → 변경할 부분 또는 변경 명령을 보냄
```

PUT에서 빠뜨린 필드의 세부 처리는 API 계약과 자원 모델에 따라 정해진다. ‘빠진 DB 컬럼이 무조건 삭제된다’는 규칙이 아니다. PATCH 본문의 형식도 API에서 명시해야 한다.

근거: [HTTP 메서드 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9), [PATCH RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html), [MDN 메서드 안내](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods).

## 4.3 안전성: 클라이언트가 상태 변경을 요구하는가?

안전한 메서드는 클라이언트가 서버 상태 변경을 의도하지 않는 메서드다. GET·HEAD·OPTIONS 등이 해당한다.

조회 로그가 쌓이거나 통계가 바뀐다고 안전성이 깨지는 것은 아니다. 부수적인 기록과 클라이언트가 요청한 업무 변경을 구분한다. 링크 미리보기·검색 수집기가 GET을 호출할 수 있으므로 조회 요청으로 주문·삭제를 실행하면 문제가 생길 수 있다.

## 4.4 멱등성: 같은 요청을 반복했을 때 의도한 효과가 같은가?

| 메서드 | 안전함 | 의미상 멱등적임 |
|---|---|---|
| GET·HEAD·OPTIONS | 예 | 예 |
| PUT | 아니요 | 예 |
| DELETE | 아니요 | 예 |
| POST | 아니요 | 일반적으로 보장하지 않음 |
| PATCH | 아니요 | 일반적으로 보장하지 않음. 변경 방식에 따라 가능 |

```text
PUT: 가격을 50000으로 설정
한 번 실행 → 50000
다시 실행 → 50000

PATCH로 설계한 증가 작업: 재고를 1 증가
한 번 실행 → +1
다시 실행 → +2
```

멱등성은 응답 내용이나 상태 코드가 매번 같아야 한다는 뜻이 아니다. DELETE를 처음 호출했을 때 204, 다시 호출했을 때 404여도 대상이 없는 상태라는 의도한 효과는 같다. 외부 사용자가 그사이 자원을 바꾼 경우까지 같은 결과를 보장한다는 뜻도 아니다.

### 재시도에서 왜 중요할까?

주문 POST를 보냈는데 응답만 유실되면 클라이언트는 주문 생성 여부를 모른다. 무조건 재시도하면 주문이 중복될 수 있다. 애플리케이션의 중복 방지 키·처리 결과 조회 등이 필요하다. TCP 재전송과 HTTP 요청을 새로 실행하는 것은 다른 일이다.

## 4.5 캐시 가능성과 멱등성은 다르다

캐시 가능성은 응답을 저장·재사용할 수 있는가에 관한 속성이다. GET·HEAD 응답은 대표적인 캐시 대상이지만, 헤더와 상태 코드 등 조건에 따라 달라진다. POST 응답도 정해진 조건에서는 캐시 가능하나 일반적인 구현 지원은 제한적이다.

**안전함 = 멱등적임 = 캐시됨**으로 외우지 않는다. 각각 다른 질문에 답하는 성질이다. 자세한 캐시 정책은 [[08_캐시와 조건부 요청]]에서 다룬다.

# 5. 데이터 전송과 API 설계

> 출발 질문: 검색 조건, 가입 폼, 파일 업로드, 주문 JSON을 모두 같은 방식으로 보내면 될까?

## 5.1 데이터를 어디에 담을까?

| 상황 | 대표 방식 | 예시 |
|---|---|---|
| 검색·필터·페이지 | URL 쿼리 | `GET /products?q=book&page=2` |
| 단순 HTML 폼 제출 | URL 인코딩 본문 | `name=A&age=20` |
| 파일과 입력값 함께 업로드 | multipart 본문 | 프로필 사진과 닉네임 |
| 프로그램 간 구조화된 데이터 | JSON 본문 등 | 주문 항목 목록 |

메서드는 동작 의미, Content-Type은 본문 형식이다. POST라고 자동으로 JSON인 것은 아니다.

## 5.2 HTML form 전송

기본 HTML 폼은 보통 GET 또는 POST로 제출한다. PUT·PATCH·DELETE는 스크립트 요청이나 별도 처리 등이 필요하다.

```html
<form method="post" action="/users">
  <input name="name" value="A">
  <button type="submit">등록</button>
</form>
```

대표적인 전송 형식:

```http
POST /users HTTP/1.1
Host: example.com
Content-Type: application/x-www-form-urlencoded

name=A
```

GET 폼이면 입력값을 쿼리로 구성한다. POST 본문이라고 암호화되는 것은 아니므로 전송 보호에는 HTTPS가 필요하다. URL은 방문 기록·로그 등에 남을 수 있으므로 민감한 비밀을 쿼리로 보내지 않는다.

## 5.3 파일 업로드와 multipart

`multipart/form-data`는 본문을 여러 파트로 나누고 각 파트에 이름·파일명·형식 등을 붙일 수 있다.

```text
multipart 본문
├─ 파트 1: name="nickname" → A
└─ 파트 2: name="photo"; filename="profile.png" → 이미지 바이트
```

파트 경계는 boundary 값으로 구분한다. 브라우저의 FormData를 사용할 때는 브라우저가 올바른 경계와 Content-Type을 생성하게 두는 것이 일반적이다. 파일 업로드와 HTTP/1.1 chunked 전송은 서로 다른 개념이다.

## 5.4 JSON API

```http
POST /orders HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json

{"items":[{"productId":10,"quantity":2}]}
```

Content-Type은 **보내는 본문이 무엇인지**, Accept는 **어떤 응답 표현을 선호하는지**를 알린다. 서버는 JSON 문법 검증과 별개로 상품 존재 여부·수량 범위·주문 권한 같은 업무 검증도 수행한다.

요청 형식 참고: [MDN HTTP 메시지](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages), [콘텐츠 협상](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Content_negotiation).

## 5.5 자원 중심으로 API를 구성하기

상품·주문을 다루는 예다.

| 목적 | 예시 | 설명 |
|---|---|---|
| 상품 목록 | `GET /products` | 컬렉션 조회 |
| 특정 상품 | `GET /products/10` | 개별 문서·자원 |
| 상품 생성 | `POST /products` | 서버가 생성 URI를 정하는 방식 |
| 특정 경로에 저장 | `PUT /files/report.txt` | 클라이언트가 대상 URI를 지정하는 저장소 방식 |
| 상품 수정 | `PATCH /products/10` | 계약에서 정한 부분 변경 |
| 주문 생성 | `POST /orders` | 주문 자원 생성 |
| 취소 요청 생성 | `POST /orders/123/cancellations` | 취소를 별도 자원으로 모델링한 예 |

복잡한 작업을 항상 CRUD에 억지로 끼워 넣을 필요는 없다. `POST /orders/123/cancel` 같은 동작형 엔드포인트를 선택할 수도 있다. 자원 모델·클라이언트 사용 방식·일관성을 고려해 계약을 명확히 한다.

### URI를 정할 때 확인할 것

- 목록과 개별 항목을 일관되게 구분하는가?
- 필터·정렬·페이지 조건의 의미가 문서화되어 있는가?
- 메서드가 실제 수행하는 동작과 일치하는가?
- 응답 상태·필드·오류 형태가 예측 가능한가?
- 다른 사용자의 자원을 다룰 때 권한 검증이 있는가?

`/users/42`를 안다고 사용자 42의 정보에 접근할 권한이 생기는 것은 아니다. 주소 식별과 인증·인가를 분리한다.

## 5.6 HTTP API와 REST는 같은 말이 아니다

HTTP는 프로토콜, API는 프로그램 간 인터페이스, REST는 아키텍처 스타일이다. REST에는 무상태성·캐시·계층 구조·일관된 인터페이스 등의 제약이 있다. 명사형 URL과 메서드를 사용한 것만으로 모든 REST 제약을 만족하는 것은 아니다. 실무에서 REST API라는 이름이 더 넓게 사용되기도 한다.

이 교재의 API 예시는 **HTTP 의미를 살려 설계하는 연습**이며, 모든 REST 제약을 구현한 완성 모델이라고 가정하지 않는다.

## 5.7 중복 주문과 동시 수정

### 주문 요청 중복

```text
클라이언트 → 주문 생성 요청 → 서버가 주문 저장
클라이언트 ← 응답 손실       ← 서버 응답
클라이언트 → 같은 의도로 재요청
```

처리 방안의 한 예는 애플리케이션의 **중복 방지 키**다. 같은 사용자·같은 키·같은 요청을 다시 받으면 새 주문 대신 기존 결과를 돌려주도록 설계한다. 키가 같지만 본문이 다른 경우, 키 보관 기간, 동시에 들어온 요청의 원자적 처리는 별도로 정의해야 한다. 헤더 이름 하나를 붙이는 것만으로 기능이 생기지 않는다.

### 동시 수정

두 사람이 오래된 상품 정보를 수정하면 뒤의 요청이 앞의 수정을 덮을 수 있다. ETag와 If-Match를 사용해 ‘내가 읽었던 버전일 때만 수정’하도록 구성할 수 있다. 실패하면 `412 Precondition Failed`로 새 상태 확인을 유도한다. [[08_캐시와 조건부 요청]]에서 이어서 다룬다.

HTTP 조건부 요청 근거: [RFC 9110 조건부 요청](https://www.rfc-editor.org/rfc/rfc9110.html#section-13).

# 6. HTTP 상태 코드

> 출발 질문: 서버와 통신은 성공했지만 주문은 실패했다면 어떤 응답을 해야 할까?

## 6.1 상태 코드는 처리 결과의 공통 표현이다

상태 코드는 응답의 의미를 클라이언트·프록시·도구가 공통으로 해석하게 한다. 본문에 `"success":false`를 넣는 것만으로 HTTP 상태 코드의 역할을 대신할 수는 없다.

| 범위 | 분류 | 읽는 방법 |
|---|---|---|
| 1xx | 정보성 | 최종 응답 전의 처리 정보 |
| 2xx | 성공 | 요청이 성공적으로 수신·처리됨 |
| 3xx | 리다이렉션 등 | 다른 위치 사용이나 저장된 표현 활용 등에 관한 응답 |
| 4xx | 클라이언트 오류 | 요청·인증·권한·현재 조건 등의 문제 |
| 5xx | 서버 오류 | 서버 측에서 요청을 수행하지 못함 |

4xx는 개발자가 사용자를 비난하는 분류가 아니다. 클라이언트가 어떤 조건을 고쳐야 하는지 전달하는 의미다. 알 수 없는 코드는 첫 자리의 분류도 참고하되, 특정 코드를 임의로 성공 취급하지 않는다.

## 6.2 주요 성공 응답

| 코드 | 의미 | 선택 예시 |
|---|---|---|
| 200 OK | 성공 | 상품 조회·처리 결과 응답 |
| 201 Created | 자원 생성 | 주문을 생성하고 새 URI 전달 |
| 202 Accepted | 처리 요청 수락 | 비동기 작업 접수. 완료를 보장하는 코드가 아님 |
| 204 No Content | 성공, 응답 콘텐츠 없음 | 삭제 성공 후 본문 불필요 |
| 206 Partial Content | 범위 요청에 대한 부분 응답 | 파일의 일부 바이트 전송 |

```http
HTTP/1.1 201 Created
Location: /orders/123
Content-Type: application/json

{"id":123,"status":"created"}
```

Location은 생성된 자원의 위치를 알리는 데도 사용된다. Location이 있다고 모든 응답이 리다이렉션은 아니다. **204에는 JSON 본문을 넣지 않는다.**

## 6.3 리다이렉션과 메서드 유지

```text
클라이언트 → GET /old
서버       → 301 + Location: /new
클라이언트 → GET /new
```

리다이렉션을 따르는 클라이언트는 Location을 해석해 새 요청을 보낸다. 서버가 기존 TCP 요청을 물리적으로 다른 서버에 옮겨 꽂는 것이 아니다.

| 코드 | 주요 의미 | 메서드 처리 |
|---|---|---|
| 301 | 영구 이동 | POST를 GET으로 바꾸는 동작이 허용됨 |
| 302 | 일시적 다른 위치 | POST를 GET으로 바꾸는 동작이 허용됨 |
| 303 | 결과를 다른 자원에서 조회 | 보통 GET, HEAD라면 HEAD로 조회 |
| 307 | 일시적 리다이렉션 | 자동으로 따를 때 메서드를 변경하지 않음 |
| 308 | 영구 리다이렉션 | 자동으로 따를 때 메서드를 변경하지 않음 |

메서드·본문 유지가 중요하면 301·302의 관행에 기대지 말고 의도를 명확하게 한다. 클라이언트가 리다이렉션을 자동으로 따르지 않을 수도 있다.

### POST → Redirect → GET, PRG

```text
폼 POST /orders
     ↓ 주문 생성
303 Location: /orders/123
     ↓
GET /orders/123
     ↓
완료 화면에서 새로고침 → GET 재요청
```

완료 화면 새로고침이 원래 POST를 반복하는 문제를 줄인다. 그러나 빠른 중복 클릭·네트워크 재시도까지 막는 완전한 중복 주문 방지책은 아니다.

### 304 Not Modified

304는 캐시 검증에서 사용한다. 조건부 GET·HEAD에서 저장된 표현이 여전히 유효할 때 반환한다. **새 페이지로 이동하라는 뜻이 아니며 응답 본문을 보내지 않는다.** 브라우저는 캐시에 있는 데이터를 재사용한다.

근거: [MDN 리다이렉션](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections), [RFC 9110 상태 코드](https://www.rfc-editor.org/rfc/rfc9110.html#section-15).

## 6.4 주요 4xx 응답

| 코드 | 판단 기준 | 예시 |
|---|---|---|
| 400 Bad Request | 요청 문법·구성 등이 잘못됨 | JSON 파싱 실패 |
| 401 Unauthorized | 유효한 인증 자격이 필요함 | 로그인 정보 없음·만료 |
| 403 Forbidden | 요청을 이해했지만 수행 거절 | 다른 사용자 주문 접근 금지 |
| 404 Not Found | 대상 없음 또는 존재를 공개하지 않음 | 없는 상품 ID |
| 405 Method Not Allowed | 해당 대상에서 메서드 불허 | 조회 전용 대상에 DELETE |
| 409 Conflict | 현재 자원 상태와 충돌 | 이미 취소된 주문의 처리 충돌 |
| 412 Precondition Failed | 요청의 전제 조건 실패 | If-Match 버전 불일치 |
| 415 Unsupported Media Type | 본문 형식 등을 지원하지 않음 | JSON만 받는데 다른 형식 제출 |
| 422 Unprocessable Content | 형식은 이해했으나 내용 처리 불가 | 계약상 허용하지 않는 값 |
| 429 Too Many Requests | 요청 빈도 제한 | 짧은 시간 내 과도한 요청 |

400과 422 등은 API의 오류 정책을 일관되게 정해야 한다. 401에는 HTTP 인증 규칙에 맞는 WWW-Authenticate 챌린지가 요구된다. 405에는 허용 메서드를 나타내는 Allow가 필요하다.

‘인증됨’과 ‘권한 있음’은 다르다. 로그인한 사용자도 타인의 데이터에 접근할 권한은 없을 수 있다.

## 6.5 주요 5xx 응답

| 코드 | 의미 |
|---|---|
| 500 Internal Server Error | 예상하지 못한 서버 내부 실패 |
| 502 Bad Gateway | 게이트웨이·프록시가 상위 서버에서 유효하지 않은 응답을 받음 |
| 503 Service Unavailable | 일시적인 과부하·점검 등으로 서비스 제공 불가 |
| 504 Gateway Timeout | 게이트웨이·프록시가 필요한 상위 응답을 제때 받지 못함 |

클라이언트 입력 오류를 모두 500으로 처리하면 원인과 대응을 판단하기 어렵다. 반대로 5xx라고 무조건 즉시 재시도하지도 않는다. 메서드의 멱등성, Retry-After, 지수적 대기 등을 함께 고려한다.

## 6.6 오류 본문은 행동할 수 있게 만든다

```json
{
  "code": "INVALID_QUANTITY",
  "message": "수량은 1 이상이어야 합니다.",
  "field": "quantity"
}
```

위 필드명은 예시 API의 계약이지 HTTP의 필수 규격이 아니다. 상태 코드는 공통 분류를, 오류 본문은 업무상 이유와 필요한 행동을 전달한다. 내부 스택 추적이나 비밀 값을 그대로 공개하지 않는다.

상태 코드 참고: [MDN 상태 코드 목록](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status).

# 7. HTTP 헤더와 쿠키

> 출발 질문: 같은 URL의 응답을 한국어·영어, JSON·HTML로 다르게 줄 수 있을까?

## 7.1 헤더는 메시지 해석·처리에 필요한 정보다

```http
GET /products/10 HTTP/1.1
Host: example.com
Accept: application/json
Accept-Language: ko, en;q=0.8

```

본문이 없는 요청도 헤더를 가질 수 있다. 헤더가 모두 ‘부가적인 선택 사항’인 것은 아니다. 예를 들어 HTTP/1.1 요청의 Host는 필수이며, 메시지 경계에 필요한 필드도 있다.

## 7.2 자원과 표현

자원은 상품 10번이라는 대상이고, 표현은 그 대상을 클라이언트에 보여 주는 형태다. 같은 상품을 JSON이나 HTML로 표현할 수 있다.

| 헤더 | 의미 | 예시 |
|---|---|---|
| Content-Type | 콘텐츠의 미디어 타입 | `application/json` |
| Content-Encoding | 콘텐츠에 적용한 인코딩 | `gzip` |
| Content-Language | 표현의 언어 | `ko` |
| Content-Length | 해당 메시지에서 규칙에 따라 해석하는 바이트 길이 | `12` |

gzip 압축과 UTF-8 문자 인코딩은 다르다. 문자셋은 `Content-Type: text/html; charset=utf-8`처럼 전달할 수 있다. 압축된 메시지에서 Content-Length를 사용한다면 일반적으로 압축된 콘텐츠의 전송 바이트 길이를 나타낸다.

## 7.3 콘텐츠 협상

클라이언트는 선호를 알리고 서버는 지원 가능한 표현을 선택한다.

| 요청 헤더 | 원하는 응답의 조건 |
|---|---|
| Accept | 미디어 타입 |
| Accept-Language | 언어 |
| Accept-Encoding | 압축 등 콘텐츠 인코딩 |

`en;q=0.8`의 q는 상대적 선호도다. 큰 값을 우선 선호하며, 0은 허용하지 않음을 나타낸다. 서버가 모든 요청 언어를 지원하는 것은 아니다.

응답이 Accept-Language에 따라 달라진다면 `Vary: Accept-Language`처럼 캐시가 구분해야 할 요청 헤더를 알릴 수 있다. [[08_캐시와 조건부 요청]]과 연결되는 부분이다.

근거: [MDN 콘텐츠 협상](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Content_negotiation).

## 7.4 길이·청크·범위 전송

| 방식 | 핵심 |
|---|---|
| 길이를 아는 전송 | Content-Length 등으로 경계 지정 |
| HTTP/1.1 chunked | 본문을 크기가 붙은 청크들로 나눠 전송 |
| 압축 | gzip 등으로 콘텐츠 자체의 크기 감소 |
| 범위 요청 | Range로 원하는 부분만 요청하고 206 등으로 응답 |

청크 전송은 ‘한 HTTP 본문을 어떻게 구분해 전달하는가’, 범위 요청은 ‘자원의 어느 부분을 달라는가’다. 둘은 별개다. HTTP/2·3에서는 프레임으로 전달하며 HTTP/1.1의 chunked 방식을 그대로 쓰지 않는다.

```http
GET /large-file HTTP/1.1
Host: example.com
Range: bytes=0-999

```

지원하는 서버는 206과 Content-Range 등을 보낼 수 있다. 서버가 Range를 항상 수용하는 것은 아니다. [HTTP/1.1 전송 구문](https://www.rfc-editor.org/rfc/rfc9112.html), [RFC 9110 범위 요청](https://www.rfc-editor.org/rfc/rfc9110.html#section-14).

## 7.5 자주 만나는 일반·특수 정보

| 헤더 | 읽는 법 |
|---|---|
| Host | 요청 대상 호스트. HTTP/2·3에는 대응하는 `:authority`가 있음 |
| User-Agent | 요청을 생성한 소프트웨어 정보. 신원 보증은 아님 |
| Referer | 유입 문서 등의 정보. 정책에 따라 생략·축소될 수 있음 |
| Date | 메시지 생성 시각 |
| Server | 서버 소프트웨어 정보 등. 생략될 수 있음 |
| Location | 리다이렉션 대상 또는 생성한 자원 위치 등 |
| Allow | 대상에서 허용하는 메서드 |
| Retry-After | 다시 시도할 시점·대기 시간 안내 |
| Content-Disposition | 인라인 표시나 다운로드, 파일명 등의 힌트 |

헤더의 존재만으로 특정 업무 결과를 단정하지 말고 상태 코드·메서드와 함께 읽는다. [헤더·메시지 의미 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).

## 7.6 인증과 인가

- **인증(Authentication):** 누구인지 또는 유효한 자격을 가졌는지 확인.
- **인가(Authorization):** 그 대상에게 어떤 작업을 허용할지 결정.

```http
Authorization: Bearer <토큰>
```

Bearer는 그 값을 가진 주체가 사용할 수 있는 자격 증명 방식이다. Bearer라고 항상 JWT인 것은 아니다. Basic 인증은 자격 정보를 Base64로 표현하지만 Base64는 암호화가 아니다. 민감한 자격 증명의 전송에는 HTTPS가 필요하다.

서버는 필요한 인증 방식을 WWW-Authenticate로 알릴 수 있다. 인증 성공 후에도 자원별 권한 검사는 별도로 해야 한다. [MDN HTTP 인증](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication).

## 7.7 쿠키: 브라우저의 저장·자동 전송 기능

서버 응답:

```http
Set-Cookie: sid=abc123; Path=/; Secure; HttpOnly; SameSite=Lax
```

이후 조건에 맞는 요청:

```http
Cookie: sid=abc123
```

브라우저는 쿠키를 자신이 관리하는 저장소에 기록하고, 요청 대상·보안 조건·정책에 맞을 때 전송한다. 디스크와 메모리 등 실제 관리 방식은 구현에 따라 다르다. 다운로드 폴더에 사용자가 지정한 파일로 저장하는 기능은 아니다.

| 속성 | 의미 |
|---|---|
| Domain | 전송 대상 도메인 범위. 생략하면 보통 설정한 호스트에 한정 |
| Path | 경로에 따른 전송 범위. 접근 제어 수단 자체는 아님 |
| Max-Age / Expires | 쿠키의 수명 설정 |
| Secure | 일반적으로 HTTPS 같은 안전한 연결로만 전송 |
| HttpOnly | 브라우저 스크립트의 일반적인 쿠키 읽기 접근 제한 |
| SameSite | 다른 사이트 문맥의 요청에 쿠키를 보낼 조건 제어 |

서로 다른 사이트의 모든 요청에 쿠키가 무조건 붙는 것은 아니다. SameSite·브라우저 개인정보 정책 등도 적용된다. SameSite의 site와 CORS의 origin은 같은 기준이 아니다.

HttpOnly여도 브라우저의 정상 HTTP 요청에는 쿠키가 포함될 수 있다. 쿠키가 자동 전송되므로 권한 있는 동작에는 CSRF 방어 등도 필요하다. SameSite 하나가 모든 공격을 해결하지는 않는다.

근거: [쿠키 RFC 6265](https://www.rfc-editor.org/rfc/rfc6265.html), [MDN 쿠키와 현대 브라우저 속성](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Cookies).

## 7.8 웹 세션: 여러 요청을 같은 이용 상태로 연결

```text
브라우저 쿠키                   서버의 세션 저장소
sid=abc123 ─────────────────→ abc123 → userId=42, 만료 시각 등
```

로그인 성공 시 서버가 세션을 만들고 ID를 전달한다. 다음 요청에서 ID를 받아 세션을 조회한다. 세션 저장소는 메모리·DB·공유 저장소 등으로 구성할 수 있다.

브라우저 쿠키의 수명과 서버 세션의 수명은 다르다. 쿠키가 있어도 세션이 만료되면 인증이 실패할 수 있다. 로그아웃은 일반적으로 서버 세션 무효화와 쿠키 제거를 함께 처리한다.

**TCP 연결을 새로 만들어도 같은 세션 ID로 로그인 상태를 이어 갈 수 있다.** 로그인 세션은 전송 연결과 별개다. 세션은 익명 장바구니 등 로그인 외의 상태에도 사용한다.

## 7.9 JWT와 비교하기

일반적인 서명형 JWT는 다음처럼 구성된다.

```text
헤더.페이로드.서명
```

페이로드에는 사용자 식별자·발급자·대상·만료 시각 등의 클레임을 담을 수 있다. 서버는 신뢰하는 키와 허용한 알고리즘으로 서명, 발급자·대상·유효기간 등 필요한 조건을 검증한다. 문자열을 디코딩해 사용자 ID를 읽었다고 인증이 끝난 것은 아니다.

| 개념 | 분류 |
|---|---|
| 쿠키 | 브라우저 저장·전송 수단 |
| 서버 측 세션 | 서버가 유지하는 이용 상태 |
| JWT | 정보를 담는 토큰 형식 |

JWT를 쿠키에 넣을 수도 있고 Authorization 헤더로 보낼 수도 있다. JWT 서명은 암호화가 아니므로 일반적인 서명형 토큰의 내용은 읽을 수 있다. 별도의 암호화 토큰 형식도 있지만 여기서는 서명형을 기준으로 한다.

서버 세션은 저장소에서 무효화할 수 있다. 자체 검증 JWT는 이미 발급된 값을 즉시 폐기하려면 별도 상태·설계가 필요할 수 있다. JWT를 쓴다고 전체 시스템이 무상태가 되는 것도 아니다. [JWT RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html).

# 8. 캐시와 조건부 요청

> 출발 질문: 캐시에 저장한 데이터가 오래되면 지우고 전체를 다시 받아야만 할까?

## 8.1 캐시는 실제 응답 데이터를 보관한다

HTTP 캐시는 응답 본문뿐 아니라 상태·헤더·재사용 판단에 필요한 정보 등을 저장한다. 같은 요청에 재사용하면 전송량과 지연·서버 작업을 줄일 수 있다.

| 캐시 | 위치 | 주 사용자 |
|---|---|---|
| 브라우저 캐시 | 내 기기의 메모리·브라우저 관리 디스크 공간 | 해당 사용자 |
| 공유 프록시·CDN 캐시 | 중간 서버의 메모리·저장장치 | 여러 사용자 |
| 애플리케이션 캐시 | 프로그램 내부·별도 저장소 | 프로그램 설계에 따름 |

이 단원은 HTTP 캐시다. CPU의 L1·L2 캐시나 DB 조회 결과 캐시와는 관리 규칙이 다르다. 저장소의 공간·정책 때문에 만료 전에 제거될 수도 있으므로 캐시가 반드시 남아 있다고 보장하지 않는다.

## 8.2 캐시를 읽는 세 질문

1. **저장 가능한가?** 요청·응답·헤더 등의 조건을 확인한다.
2. **바로 재사용 가능한가?** 신선도와 캐시 키 등을 확인한다.
3. **오래됐다면 검증할 수 있는가?** ETag·수정 시각 등의 검증자를 사용한다.

저장 가능과 즉시 재사용 가능은 다르다. 같은 URL이라고 무조건 같은 응답도 아니다. 요청 메서드, Vary가 지정한 헤더 등의 요소가 재사용 판단에 영향을 준다.

## 8.3 신선도와 max-age

```http
Cache-Control: public, max-age=60
ETag: "product-10-v1"
```

다른 조건을 만족하면 max-age가 정한 시간 동안 신선한 응답으로 재사용할 수 있다.

```text
최초 요청 → 서버가 200 + 본문 + 캐시 정책 응답
                    ↓
신선한 동안 다시 필요 → 저장된 응답 사용 가능
                    ↓
오래된 뒤 다시 필요 → 정책에 맞게 서버 재검증 등
```

max-age를 ‘브라우저가 다운로드한 순간부터 무조건 N초’로만 계산하면 부정확하다. Date·Age와 응답 이동 시간 등을 고려하는 캐시 나이 계산이 있다. `max-age=60`인 응답이 이미 Age=50이면 새 브라우저에 도착했다고 60초가 새로 시작하는 것은 아니다.

신선하다고 실제 서버 데이터가 반드시 같은 것도 아니다. TTL은 허용할 재사용 기간에 대한 정책이다. 정책이 허용하는 오래된 응답 사용의 별도 예외도 있지만, 처음에는 ‘신선도 만료 후 재검증’을 기본 흐름으로 이해한다.

근거: [HTTP 캐시 RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html).

## 8.4 Cache-Control을 구분하기

| 응답 지시어 | 의미 |
|---|---|
| max-age=N | 신선도 수명을 초 단위로 지정 |
| s-maxage=N | 공유 캐시에 적용하는 신선도 정책 |
| public | 공유 캐시에서의 저장·재사용을 허용하는 명시적 지시. 다른 규칙도 적용 |
| private | 공유 캐시 저장 금지. 개인 브라우저 캐시는 가능 |
| no-cache | 저장은 가능하지만 재사용 전 성공적인 검증 필요 |
| no-store | 이 요청·응답을 캐시에 저장하지 말라는 지시 |
| must-revalidate | 신선도가 지난 응답을 검증 없이 재사용하지 말라는 지시 |

`Expires`도 만료 시각을 나타내지만 max-age가 함께 있으면 해당 규칙이 우선한다. `Pragma: no-cache`는 오래된 호환 동작과 관련되므로 현대 캐시 제어의 주 수단으로만 의존하지 않는다.

### no-cache와 no-store

```text
no-cache → “보관해도 돼. 하지만 쓰기 전에 확인해.”
no-store → “이 응답을 보관하지 마.”
```

no-store는 이미 다른 응답으로 저장돼 있던 모든 캐시를 삭제하는 명령이 아니다. private도 암호화나 사용자 인증 기능이 아니다. 민감한 응답은 내용·보안 정책에 맞춰 저장 여부를 정한다.

근거: [MDN Cache-Control](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control).

## 8.5 ETag로 바뀌었는지 확인하기

최초 응답의 주요 부분:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: max-age=60
ETag: "product-10-v1"

{"id":10,"name":"키보드"}
```

신선도가 지난 뒤 검증 요청:

```http
GET /products/10 HTTP/1.1
Host: example.com
If-None-Match: "product-10-v1"

```

서버 판단은 두 갈래다.

```text
현재 표현과 검증자가 일치
→ 304 Not Modified + 관련 헤더, 본문 없음
→ 캐시의 저장된 본문을 재사용하고 메타데이터 갱신

표현이 변경됨
→ 200 OK + 새 ETag + 새 본문
→ 새 응답으로 캐시 갱신
```

ETag는 서버가 정하는 검증자다. 반드시 파일 해시일 필요는 없으며 값의 내부 형식을 클라이언트가 추측해서 처리하지 않는다. `W/`가 붙은 약한 검증자와 강한 검증자는 비교에 사용되는 규칙이 다르다.

## 8.6 Last-Modified와 조건부 요청

```text
응답: Last-Modified: Mon, 19 Oct 2026 01:00:00 GMT
재검증: If-Modified-Since: Mon, 19 Oct 2026 01:00:00 GMT
```

수정 시각을 기준으로 변경 여부를 확인할 수 있다. 시간 정밀도·시각 관리 등 한계가 있으므로 표현 버전을 정교하게 구분할 때 ETag가 유용하다. 일반적인 GET 재검증에서 If-None-Match와 If-Modified-Since가 함께 있으면 If-None-Match가 우선한다.

### 수정 충돌 방지: If-Match

```http
PATCH /products/10 HTTP/1.1
Host: example.com
If-Match: "product-10-v1"
Content-Type: application/json

{"price":60000}
```

서버가 가진 버전이 이미 v2라면 조건이 맞지 않아 412로 거절할 수 있다. ‘바뀌지 않았으면 기존 본문 재사용’인 If-None-Match와 ‘내가 본 버전일 때만 변경’인 If-Match를 구분한다. If-Match에는 강한 비교 규칙이 사용된다.

근거: [MDN 조건부 요청](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests), [RFC 9110 검증자·전제 조건](https://www.rfc-editor.org/rfc/rfc9110.html#section-13).

## 8.7 프록시 캐시와 Vary

```text
사용자 A ─┐
사용자 B ─┼─ CDN·공유 캐시 ─ 원본 서버
사용자 C ─┘
```

같은 공개 이미지의 복사본을 공유하면 원본 서버 부담을 줄인다. 반대로 사용자 A의 개인정보를 사용자 B에게 재사용하면 안 된다.

언어별 응답 예:

```http
Vary: Accept-Language
```

캐시는 요청의 Accept-Language도 구분해야 한다. Vary는 보안 권한 검사 자체가 아니다. 사용자별 응답을 안전하게 공유하는 기능으로 오해하지 않는다. 캐시 키 설계와 private·no-store 등 정책을 함께 고려한다.

## 8.8 캐시 무효화와 파일 버전

서버 파일이 바뀌었다고 이미 신선한 캐시가 즉시 이를 알지는 못한다. 방법을 선택해야 한다.

- **짧은 TTL:** 변경 반영 지연을 줄이고 재검증을 늘린다.
- **검증자:** 오래된 응답의 변경 여부를 확인한다.
- **버전 URL:** `app.a1b2.js`처럼 내용이 달라지면 새 URL을 사용한다.
- **CDN purge:** 사업자의 캐시 삭제 기능을 사용한다. 모든 브라우저 캐시까지 삭제하는 것은 아니다.

버전이 고정된 정적 파일에는 긴 캐시 수명을 적용하고, 그 파일을 참조하는 HTML은 더 자주 갱신하는 식으로 구성할 수 있다.

# 9. 실습과 종합 과제

본문을 다 외운 뒤가 아니라, 읽은 개념이 실제 응답에서 보이는지 확인하면서 공부한다. 아래 실습은 인터넷의 외부 서비스에 데이터를 쓰지 않고 내 컴퓨터의 서버만 사용한다.

## 9.1 실습 준비

함께 제공한 [로컬 실습 서버](실습/http_lab.py)는 Python 표준 라이브러리만 사용한다. Python 3가 준비된 환경에서 실행할 수 있다.

터미널 하나를 열어 다음을 실행한다.

```bash
python3 "/Users/user/Documents/Study/Obsidian/Java/네트워크/HTTP_학습자료/실습/http_lab.py"
```

브라우저에서 [http://127.0.0.1:8765](http://127.0.0.1:8765)를 연다. `127.0.0.1`은 자신의 컴퓨터다. 서버를 켠 터미널은 그대로 두고, 요청 명령은 두 번째 터미널에서 실행한다. 중지하려면 서버 터미널에서 Ctrl+C를 누른다.

8765 포트가 사용 중이라면 `--port 8766` 등을 붙이고 예시 주소도 함께 바꾼다. 요청에 사용한 `example.com`은 문서용이지만 이 로컬 주소는 실제로 동작한다.

### 실습 서버의 범위

- 프로세스를 재시작하면 상품 변경·세션·주문 기록이 모두 초기화된다.
- 모의 로그인은 비밀번호 검증 없이 사용자 42번의 세션을 만든다. **인증 기능 자체의 구현 예제가 아니라 쿠키·세션 흐름 관찰용**이다.
- 로컬 HTTP 실습이므로 쿠키에 Secure를 생략했다. 실제 서비스의 HTTPS·보안 설정을 대체하지 않는다.
- `/cache`의 버전과 `/products/10`의 버전은 별도로 관리한다.
- 기본 요청 경계만 구현하므로 모든 HTTP 기능을 지원하는 운영용 서버는 아니다. 요청 본문은 1MiB 이하로 제한한다.

## 9.2 실습 1 — 요청·응답의 기본 구조

```bash
curl -i http://127.0.0.1:8765/products/10
```

확인할 것:

1. 첫 줄의 상태 코드가 200인가?
2. Content-Type이 JSON인가?
3. 헤더와 본문 사이에 빈 줄이 있는가?
4. 본문에 상품 id·name·price가 있는가?
5. Content-Length와 ETag는 무엇을 뜻하는가?

브라우저 개발자도구의 Network에서 같은 요청을 보고 Headers와 Response를 구분한다. 브라우저 메뉴·단축키는 버전에 따라 다를 수 있으므로 도구 이름으로 찾는다.

## 9.3 실습 2 — 쿼리·폼·JSON 비교

```bash
curl -i 'http://127.0.0.1:8765/echo?q=book&page=2'
```

```bash
curl -i -d 'name=A&age=20' http://127.0.0.1:8765/echo
```

```bash
curl -i -H 'Content-Type: application/json' \
  -d '{"name":"A","age":20}' \
  http://127.0.0.1:8765/echo
```

응답의 method·query·contentType·body를 비교한다. `/echo`는 관찰을 위해 본문을 문자열로 보여 준다. JSON 본문을 보냈다고 응답의 body 필드도 자동으로 JSON 객체가 되는 것은 아니다.

브라우저 실습 첫 화면의 GET·POST 폼도 제출해 본다. 같은 입력값이 어디에 담기는지 비교한다.

## 9.4 실습 3 — HEAD·OPTIONS·오류 응답

```bash
curl -I http://127.0.0.1:8765/products/10
```

```bash
curl -i -X OPTIONS http://127.0.0.1:8765/products/10
```

```bash
curl -i -X DELETE http://127.0.0.1:8765/products/10
```

```bash
curl -i http://127.0.0.1:8765/not-found
```

예상 결과:

| 요청 | 예상 |
|---|---|
| HEAD | 200, 응답 본문 없음. 대응하는 GET의 길이 정보는 표시 가능 |
| OPTIONS | 204, Allow에 GET·HEAD·PATCH·OPTIONS |
| DELETE | 405, Allow로 허용 메서드 안내 |
| 없는 경로 | 404 |

## 9.5 실습 4 — 버전 조건을 붙여 수정

서버를 처음 시작한 상태의 ETag는 `"product-10-v1"`이다. 이미 수정했다면 GET으로 현재 ETag를 확인하고 첫 요청의 값을 바꾼다.

```bash
curl -i -X PATCH \
  -H 'Content-Type: application/json' \
  -H 'If-Match: "product-10-v1"' \
  -d '{"price":60000}' \
  http://127.0.0.1:8765/products/10
```

성공하면 200과 변경된 상품, 새 ETag를 받는다. **같은 예전 If-Match로 다시 요청하면 412**가 된다. 새 ETag를 조회하지 않고 오래된 화면으로 수정하려는 상황을 재현한 것이다.

추가 관찰:

- JSON 헤더를 빼면? → 415
- JSON 문법을 깨뜨리면? → 400
- price를 음수로 보내면? → 422

## 9.6 실습 5 — 303을 직접 보기

```bash
curl -i http://127.0.0.1:8765/redirect
```

303과 Location을 확인한다. 다음 명령에서는 리다이렉션을 따르도록 한다.

```bash
curl -i -L http://127.0.0.1:8765/redirect
```

303 응답 뒤에 상품 조회의 200 응답이 이어지는 것을 확인한다. 브라우저로 `/redirect`를 열 때는 최종 주소와 Network의 요청 순서를 관찰한다.

## 9.7 실습 6 — 쿠키와 서버 세션

먼저 쿠키 없이 호출한다.

```bash
curl -i http://127.0.0.1:8765/me
```

401이 나온다. 다음으로 모의 로그인하고 쿠키를 파일에 기록한다. 아래 파일은 실습용 쿠키 저장소다.

```bash
curl -i -X POST -c http-study-cookies.txt \
  http://127.0.0.1:8765/login
```

Set-Cookie의 sid·Path·HttpOnly·SameSite·Max-Age를 확인한다. 받은 쿠키를 다음 요청에 사용한다.

```bash
curl -i -b http-study-cookies.txt http://127.0.0.1:8765/me
```

200과 사용자 42번 정보가 나온다. 로그아웃한다.

```bash
curl -i -X POST -b http-study-cookies.txt \
  http://127.0.0.1:8765/logout
```

**기존 쿠키 파일을 그대로 다시 사용**해 본다.

```bash
curl -i -b http-study-cookies.txt http://127.0.0.1:8765/me
```

서버가 세션을 무효화했으므로 401이다. ‘브라우저에 세션 ID가 남아 있는 것’과 ‘서버에서 유효한 세션인 것’이 다름을 확인한다. 실제 브라우저는 로그아웃 응답의 Max-Age=0도 반영하지만, 이 명령은 쿠키 파일을 갱신하지 않고 일부러 예전 값을 재전송했다.

이 서버의 `WWW-Authenticate: Session ...`은 설명용 사설 인증 방식이다. 표준 브라우저 로그인 창이나 실제 인증 체계를 구현한 것이 아니다.

## 9.8 실습 7 — ETag·304·변경 후 200

```bash
curl -i http://127.0.0.1:8765/cache
```

초기 응답은 200, ETag는 `"demo-v1"`, Cache-Control은 max-age=5다. 조건부 요청을 보낸다.

```bash
curl -i -H 'If-None-Match: "demo-v1"' \
  http://127.0.0.1:8765/cache
```

304이며 응답 본문이 없다. 원본의 버전을 바꾼다.

```bash
curl -i -X POST http://127.0.0.1:8765/cache/change
```

다시 **예전 ETag**로 요청하면 이번에는 200과 새 본문·새 ETag가 나온다. 이미 버전을 변경한 상태라면 처음 받은 ETag를 기준으로 실습한다.

**일반적인 curl 호출은 브라우저처럼 HTTP 응답 캐시를 자동 유지하지 않는다.** 이 실습은 조건부 요청을 수동으로 보내 검증하는 것이다. 자동 캐시 재사용은 브라우저에서 관찰한다. Network의 Disable cache를 해제하고, 브라우저가 메모리·디스크 캐시를 사용했는지 또는 재검증했는지 확인한다. 새로고침 방식에 따라 브라우저가 신선한 응답도 재검증할 수 있다.

## 9.9 실습 8 — 주문 중복과 중복 방지 키

```bash
curl -i -H 'Content-Type: application/json' \
  -d '{"productId":10,"quantity":2}' \
  http://127.0.0.1:8765/orders
```

같은 명령을 두 번 실행하면 별도 주문 ID가 생성된다. 이번에는 같은 키를 붙여 두 번 보낸다.

```bash
curl -i -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: study-order-1' \
  -d '{"productId":10,"quantity":2}' \
  http://127.0.0.1:8765/orders
```

두 번째 응답에서도 같은 주문 ID가 나오고 `X-Demo-Replayed: true`가 붙는다. 같은 키로 quantity만 3으로 바꾸면 409다.

이는 **서버가 같은 키와 요청 내용을 기록하고 처리했기 때문에** 가능한 동작이다. 헤더를 붙였다고 모든 서버가 자동 지원하는 것이 아니다. 이 실습의 키는 단일 사용자·프로세스 수명 범위로 한정했다. 운영 시스템에서는 사용자 범위, 키 만료, 영속성, 다중 서버의 원자적 처리도 설계해야 한다.

## 9.10 종합 과제 — 작은 주문 API 설계

다음 기능을 가진 API를 문서로 설계한다. 코드를 작성하지 않아도 된다.

1. 상품 목록·상세 조회
2. 로그인 사용자의 주문 생성
3. 본인의 주문 조회
4. 주문 취소
5. 상품 정보 변경 시 동시 수정 충돌 방지
6. 공개 상품 이미지 캐시와 개인정보 응답의 캐시 정책

각 기능에 다음을 채운다.

| 항목 | 작성할 내용 |
|---|---|
| 요청 | 메서드·URI·필수 헤더·본문 |
| 인증·인가 | 자격 증명 전달 방식, 허용 대상 |
| 성공 응답 | 상태 코드·헤더·본문 |
| 오류 응답 | 입력 오류·인증 실패·권한 부족·충돌 |
| 재시도 | 중복 처리 위험과 대응 |
| 캐시 | 저장·재사용·재검증 정책 |

예시 답안은 [[10_복습 문제 해설#종합 과제 예시]]에 있다. 먼저 자신의 설계를 작성하고 비교한다.

- API를 만들기 시작한다면 입력 검증·권한 검사·에러 처리·트랜잭션·관측 가능성을 연결해서 배운다.

# 복습 문제 해설

용어를 외웠는지보다 **서로 다른 계층과 역할을 구분할 수 있는지**를 확인한다. 답을 읽은 뒤에는 자신의 예시를 하나 더 만든다.

## 1단원

1. **IP와 포트:** IP 주소만으로 같은 장비에서 제공하는 여러 통신 서비스를 충분히 구분할 수 없다. TCP·UDP 포트와 연결 끝점 정보가 필요하다. 포트 하나가 프로세스 하나와 항상 일대일 대응하는 것은 아니다.
2. **ACK=1101:** 해당 방향에서 1100까지의 연속된 바이트를 받았고 다음으로 1101을 기대한다는 의미다. 애플리케이션의 주문 저장·결제 성공까지 확인하는 것은 아니다.
3. **TCP 상태 위치:** 양쪽 운영체제가 각자 연결 상태를 관리한다. TCP 헤더의 SEQ·ACK·윈도·플래그 등을 교환해 갱신하며 내부 기록 전체를 통째로 보내지 않는다.
4. **UDP와 로그인:** 가능하다. UDP가 연결 상태를 기본 제공하지 않는 것과 게임 프로그램이 사용자를 식별하고 세션을 관리하는 것은 별개다.
5. **DNS와 라우터:** DNS는 이름에 대한 주소 등의 정보를 찾고, 라우터는 목적지 IP에 대한 다음 경로를 선택한다.

## 2단원

1. **프래그먼트:** `#reviews` 같은 부분은 보통 서버에 보내는 HTTP 요청 대상에 포함되지 않는다. 경로와 쿼리는 포함된다.
2. **DNS 성공의 한계:** IP를 알아도 연결 거부·방화벽·TLS 실패·서버 오류 등이 발생할 수 있다. 주소 조회와 서비스 성공은 다른 단계다.
3. **TCP와 TLS:** TCP는 전송 연결과 바이트 흐름을, TLS는 암호화·무결성과 인증서에 기반한 신원 확인 등을 담당한다. TCP SYN 교환이 HTTPS 인증서 검증을 대신하지 않는다.
4. **도메인과 서버 수:** DNS·로드밸런서·프록시를 통해 여러 서버가 하나의 도메인 서비스를 처리할 수 있다. 한 IP에서도 여러 사이트를 제공할 수 있다.
5. **추가 요청:** HTML이 참조한 CSS·JS·이미지 등을 가져오거나 스크립트가 API를 호출하기 때문이다. 캐시가 있으면 일부 요청·다운로드는 줄어들 수 있다.

## 3단원

1. **무상태와 DB:** HTTP 요청 간 대화 맥락을 자동 유지하지 않는다는 의미다. 상품·주문 같은 자원의 상태를 DB에 저장하는 것은 가능하다.
2. **연결 재사용:** HTTP/1.1은 보통 지속 연결을 사용한다. 무상태성을 ‘매번 연결 종료’로 해석하면 안 된다.
3. **메시지 구조:** 요청 시작 줄은 메서드·대상·버전이고, 이어지는 이름:값 줄이 헤더다. 빈 줄 뒤에 규칙에 따라 본문이 올 수 있다.
4. **바이트 길이:** Content-Length는 규칙에 따른 바이트 수다. UTF-8의 한글 등을 문자 개수로 세면 길이가 맞지 않을 수 있다.
5. **HTTP/3의 신뢰성:** UDP 위의 QUIC이 연결·손실 복구·스트림 순서·혼잡 제어 등을 제공한다. UDP 자체가 TCP처럼 바뀐 것은 아니다.

## 4단원

1. **대상과 동작:** 같은 `/products/10`이라도 GET·DELETE 메서드로 조회·삭제 요청을 구분할 수 있다. 서버가 각각 구현해야 한다.
2. **안전한 조회:** 로그 기록은 보통 부수 효과다. 안전성은 클라이언트가 업무상 상태 변경을 요청하는지에 관한 의미다.
3. **DELETE와 멱등성:** 첫 성공 후 이미 대상이 없어 두 번째에 404가 나와도 의도한 효과는 대상 제거다. 같은 상태 코드·본문을 요구하는 성질이 아니다.
4. **PUT·PATCH:** PUT은 지정 대상의 상태를 전달한 표현으로 생성·대체하는 의미다. PATCH는 부분 변경을 적용한다. 증가 명령 같은 PATCH는 반복 시 결과가 달라질 수 있다.
5. **주문 재시도:** 서버가 주문을 이미 만들었는데 응답만 못 받았을 수 있다. 중복 방지 키·결과 조회 등의 API 설계가 없으면 새 주문이 만들어질 수 있다.

## 5단원

1. **POST와 JSON:** POST는 처리 의미이고 본문 형식은 Content-Type 등 계약이 정한다. 폼·multipart·JSON 등 여러 형태가 가능하다.
2. **전송 형식:** 검색 조건은 GET 쿼리가 대표적이다. 파일과 입력값은 multipart/form-data를 사용할 수 있다. 개인정보·비밀을 URL에 노출하지 않는 설계도 고려한다.
3. **Content-Type·Accept:** 앞의 것은 실제로 보내는 콘텐츠 형식이고 뒤의 것은 선호하는 응답 형식이다. 요청과 응답의 Content-Type은 각각 그 메시지의 콘텐츠에 적용된다.
4. **생성 URI:** PUT 저장은 클라이언트가 이미 지정한 URI를 대상으로 한다. POST 컬렉션 생성은 서버가 새 자원 ID·URI를 정하는 구성이 대표적이다.
5. **중복 방지 구현:** 키와 사용자·본문·처리 결과의 관계를 기록하고 중복 실행을 원자적으로 방지해야 한다. 키만 붙이는 클라이언트 작업으로는 충분하지 않다.

## 6단원

1. **201·202:** 201은 자원이 생성됐음을 나타낸다. 202는 요청을 처리 대상으로 받아들였다는 뜻이며 최종 완료·성공을 보장하지 않는다.
2. **204:** 콘텐츠가 없는 응답이다. JSON 결과가 필요하면 200 등 상황에 맞는 다른 코드를 사용한다.
3. **307:** 일시적 리다이렉션에서 자동으로 따라갈 때 메서드를 바꾸지 않는 코드다. 영구 이동의 대응 코드는 308이다.
4. **401·403:** 401은 필요한 유효한 인증 자격이 없다는 의미다. 403은 수행을 거절한다는 뜻이며 로그인했어도 권한이 없을 수 있다. 서버는 존재 여부를 숨기기 위해 404를 선택할 수도 있다.
5. **500과 저장 여부:** 단정할 수 없다. 저장 후 응답 작성 중 실패했거나 일부 외부 작업이 완료됐을 수 있다. 트랜잭션 경계·작업 결과·중복 처리 정책을 알아야 한다.

## 7단원

1. **표현 관련 헤더:** Content-Type은 콘텐츠 형식, Accept는 원하는 응답 형식, Content-Encoding은 gzip처럼 콘텐츠에 적용된 인코딩이다.
2. **청크와 범위:** chunked는 HTTP/1.1 본문의 전송 경계 방식이고 Range는 자원의 일부를 요청하는 의미다. 파일 업로드 multipart와도 구분한다.
3. **인증과 인가:** 누구인지 확인해도 해당 주문이나 관리자 기능에 접근할 권한까지 자동으로 생기지는 않는다.
4. **쿠키·세션·JWT:** 각각 브라우저 저장·전송 수단, 서버 측 상태 관리, 토큰 형식이다. JWT를 쿠키에 담을 수도 있다. TCP 연결 상태와는 별개의 이야기다.
5. **HttpOnly:** 브라우저 스크립트가 일반적으로 쿠키 값을 읽지 못하도록 하는 속성이다. 조건에 맞는 HTTP 요청에는 쿠키가 전송될 수 있다.

## 8단원

1. **저장과 재사용:** 저장할 수 있어도 no-cache나 신선도 만료 등으로 재사용 전에 검증해야 할 수 있다. 캐시 키가 다른 요청에 저장된 응답도 그대로 사용하면 안 된다.
2. **no-cache·no-store:** 전자는 저장 후 재사용 전 검증, 후자는 저장 금지다. no-store가 과거 모든 캐시의 삭제를 보장하지는 않는다.
3. **304:** 새 본문이 없다. 클라이언트 캐시의 기존 본문을 재사용하고 필요한 헤더 정보를 갱신한다. 서버가 요청 본문을 새로 보내지 않는다고 화면이 사라지는 것은 아니다.
4. **Vary:** `Vary: Accept-Language`를 사용해 언어 요청 헤더도 응답 선택에 영향을 준다고 알릴 수 있다. 사용자 권한을 검사하는 기능은 아니다.
5. **조건의 방향:** If-None-Match는 일반적인 GET 검증에서 값이 같으면 304로 재사용하게 한다. If-Match는 조건이 맞는 버전일 때 변경 등을 수행하게 하며 불일치하면 412가 될 수 있다.

## 종합 과제 예시

유일한 정답은 아니다. 필요한 계약을 일관되게 선택했는지 확인한다.

### 1. 상품 조회

```text
GET /products?page=1
GET /products/10

성공: 200 + JSON
없는 상품: 404
정책: 공개 데이터라면 짧은 max-age와 ETag 사용 가능
```

실시간 가격·재고의 최종 판단은 주문 시 서버에서 다시 수행한다. 캐시된 화면의 가격만 신뢰해 결제 금액을 결정하지 않는다.

### 2. 주문 생성

```text
POST /orders
Content-Type: application/json
Cookie: sid=<세션 ID>
Idempotency-Key: <이번 주문 시도의 식별 키>

{"items":[{"productId":10,"quantity":2}]}

성공: 201 + Location: /orders/123 + 주문 JSON
인증 필요: 401
입력 오류: 계약에 따라 400·422
키 충돌·주문 상태 충돌: 계약에 따라 409
개인정보 포함 응답: 예시 정책 Cache-Control: no-store
```

Idempotency-Key는 이 API가 지원한다고 문서화한 계약이다. 수량·재고·가격·권한을 서버에서 검증하고 주문 생성과 중복 방지 기록의 일관성을 보장해야 한다.

### 3. 본인의 주문 조회

```text
GET /orders/123 + 인증 정보
성공: 200
인증 자격 없음: 401
다른 사용자의 주문: 정책에 따라 403 또는 존재를 숨기는 404
개인정보 응답: 예시 정책 no-store
```

세션이 유효한지와 주문 소유자인지를 따로 확인한다. URI의 주문 ID를 바꾸는 것으로 다른 사용자의 데이터에 접근하면 안 된다.

### 4. 주문 취소

```text
POST /orders/123/cancellations
성공: 취소 자원을 생성했다면 201
비동기 처리 접수라면 202 + 상태 조회 방법
이미 배송돼 취소 불가능하다면 계약에 따른 409 등
```

동작형 URI를 선택하는 것도 가능하다. 중요한 것은 취소 가능 조건·중복 요청·환불 등의 완료 기준을 명확하게 하는 것이다.

### 5. 동시 수정

```text
GET /products/10 → ETag: "v1"
PATCH /products/10 + If-Match: "v1"

현재 v1이면 수정 + 새 ETag
현재 v2이면 412, 최신 상태를 확인한 뒤 재결정
```

단순히 버전을 읽고 나중에 저장하는 두 동작 사이에도 경쟁이 생길 수 있다. 서버는 확인과 변경이 원자적으로 적용되도록 구현해야 한다.

### 6. 캐시 정책

| 대상 | 선택 가능한 예시 정책 | 이유 |
|---|---|---|
| 내용 해시가 포함된 공개 이미지 URL | 긴 max-age, 공유 캐시 허용 | 내용 변경 시 URL도 바뀜 |
| 자주 바뀌는 상품 JSON | 짧은 max-age + ETag 또는 no-cache | 재사용과 변경 확인의 균형 |
| 주문·개인정보 | no-store 등 요구에 맞춘 정책 | 민감한 결과의 저장·공유 방지 |

이 예시는 서비스 요구에 맞게 조정해야 한다. 특히 no-store를 데이터 암호화·권한 검증의 대체 수단으로 쓰지 않는다.

## 마지막 자기 설명

다음 이야기를 순서대로 말할 수 있으면 전체 구조를 연결해서 이해한 것이다.

> 브라우저가 도메인의 주소를 찾고 전송 연결을 만든다. HTTP 요청은 메서드·대상·헤더·본문으로 의미를 표현한다. 서버는 인증·권한·업무 검증 후 상태 코드와 데이터를 응답한다. TCP 연결 기록과 웹 세션은 별개이며, 쿠키는 필요한 식별 정보를 다음 요청에 실어 나를 수 있다. 캐시는 정책에 맞는 응답을 저장하고, 신선도와 검증자로 재사용 여부를 결정한다.

## 헷갈리는 쌍

| 비교 | 구분 |
|---|---|
| TCP 세션 vs 웹 세션 | 바이트 전송 상태 vs 사용자 이용 상태 |
| 쿠키 vs 캐시 | 요청에 보낼 작은 상태 정보 등의 저장 수단 vs 응답 재사용 저장 |
| 포트 vs 경로 | 전송 끝점 vs HTTP 요청 대상 |
| TCP ACK vs HTTP 200 | 상대 TCP의 수신 확인 vs 애플리케이션 프로토콜의 성공 응답 |
| HTTP 200 vs 업무상 성공 보장 | API 계약의 결과를 봐야 함. 응답이 끊겨도 업무가 수행됐을 수 있음 |
| Content-Type vs Accept | 현재 보내는 콘텐츠 형식 vs 선호하는 응답 형식 |
| Content-Encoding vs Transfer-Encoding | 콘텐츠의 인코딩 vs 전송 메시지에 적용한 코딩 |
| no-cache vs no-store | 재사용 전 검증 vs 저장 금지 |
| If-None-Match vs If-Match | 같은 버전이면 캐시 재사용 등에 활용 vs 같은 버전일 때만 처리 |
| 쿠키 Secure vs HttpOnly | 전송 연결 조건 vs 스크립트 접근 제한 |

## 공식 자료를 읽는 순서

처음에는 MDN의 개요·예시를 보고, 세부 의미가 애매할 때 해당 RFC 절을 확인한다. RFC에 있는 MUST·SHOULD·MAY는 각각 요구 수준이 다르므로 단순한 수사 표현처럼 읽지 않는다.

### 인터넷·주소·보안

- [TCP — RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html): 연결 상태, 순서 번호, 수신 확인, 종료.
- [UDP — RFC 768](https://www.rfc-editor.org/rfc/rfc768.html): 데이터그램 전송의 기본 형식.
- [DNS — RFC 1034](https://www.rfc-editor.org/rfc/rfc1034.html): 도메인과 분산 조회 개념.
- [URI — RFC 3986](https://www.rfc-editor.org/rfc/rfc3986.html): 스킴·경로·쿼리·프래그먼트 문법.
- [TLS 1.3 — RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html): 보안 연결과 인증.

### HTTP의 의미와 버전

- [HTTP Semantics — RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html): 버전에 공통인 메서드·상태 코드·헤더 의미.
- [HTTP/1.1 — RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html): 텍스트 구문·메시지 경계·연결 관리.
- [HTTP/3 — RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html): QUIC 위의 HTTP.
- [QUIC — RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html): 스트림·연결·경로 이동·신뢰성.
- [PATCH — RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html): 부분 변경 의미.

### 쿠키·토큰·캐시

- [HTTP Cookies — RFC 6265](https://www.rfc-editor.org/rfc/rfc6265.html): 쿠키의 기본 저장·전송 모델. 현대 속성·브라우저 정책은 MDN 등도 함께 확인.
- [JWT — RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html): 토큰·클레임 형식.
- [HTTP Caching — RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html): 저장·신선도·재검증·무효화.

## 교재의 범위

HTTP/1.1 형식으로 메시지를 읽는 연습을 하되, 현대 HTTP가 항상 요청마다 연결을 닫거나 텍스트 메시지만 사용한다고 가정하지 않는다. 브라우저의 캐시·쿠키 세부 정책은 제품·버전에 따라 달라질 수 있다.
