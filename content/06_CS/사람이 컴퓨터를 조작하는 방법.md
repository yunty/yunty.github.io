# 컴퓨터란?
컴퓨터는 계산한다는 뜻의 라틴어인 `Computare`에서 유래 되었으며 과거에는 계산을 하는 사람을 컴퓨터라 칭했다.

현대로 넘어오면서 입력된 데이터를 받아서 정해진 규칙대로 계산, 처리하는 기계를 뜻하게 되었다.
## Computare
> com(함께) + putare(생각하다, 셈하다) = 함께 세다 &rarr; compute &rarr; compute + er(계산하는 사람)

즉 초기의 컴퓨터는 계산을 하는 사람 즉 계산원을 지칭하는 단어였고 기계가 이를 대체하게 되면서 human computer와 electronic computer로 분리되기도 하였으며 기계로 완전 대체 되며 computer가 계산하는 기계를 칭하게 되었다.

## 초기의 컴퓨터
### 진공관 컴퓨터
> [!info]- 진공관의 작동 원리
>진공관은 음극과 양극 사이의 전자를 흐르게 하여 1을, 흐르지 않게 하여 0을 표시한다.
>
>음극을 가열하여 빠져나온 전자는 전기력으로 인해 전위차 에너지 만큼을 이동하여 양극에 도착하게 되는데 이때 중간에 그리드를 두어 -전압을 걸게되면 음극에서 나오는 전자(-)는 -에 막혀 밀려나게 되는 성질을 이용해 0을 표시한다.
>==물론 회로별로 정해지는 규칙으로 안지나가는게 1로 설정도 가능하다==

진공관 컴퓨터는 연산장치, 제어장치, 기억장치, 입출력장치, 연결·보조 장치로 구성되었다. 이 중 연산·제어·기억은 모두 0과 1로 처리된다.

켜고 끌 수 있는 스위치(진공관, 현대의 트랜지스터)의 상태로 0과 1을 표현하고, 스위치를 여러 개 이어 **게이트**(연산·제어)와 **플립플롭**(기억)을 만든다. 이것들을 모아 **가산기, 해독기, 레지스터** 등을 만들고, 이것이 모여 컴퓨터가 된다.

## 현대의 컴퓨터

### 트랜지스터 컴퓨터

> [!info]- 트랜지스터의 작동 원리

> 트랜지스터는 반도체로 만든 스위치로, 진공관의 음극·그리드·양극에 해당하는 세 단자(소스·게이트·드레인)를 가진다.

> 게이트에 전압을 걸면 전기장이 소스와 드레인 사이의 반도체에 전자가 지나갈 길(채널)을 만들어 전류가 흐르고(1), 전압을 끊으면 길이 사라져 흐르지 않는다(0).

> 진공관처럼 가열이 필요 없고, 반도체 위에 아주 작게 만들 수 있다.

현대의 컴퓨터도 구조는 진공관 컴퓨터와 같다. 켜고 끌 수 있는 스위치(트랜지스터)의 상태로 0과 1을 표현하고, 이를 이어 **게이트**(연산·제어)와 **플립플롭**(기억)을 만들고, 이것들을 모아 가산기, 해독기, 레지스터 등을 만든다.

달라진 것은 스위치의 재료와 규모이다. 트랜지스터 수십억 개를 **집적회로(칩)** 한 장에 새겨 넣었다.

#### 구성

| 구성 | 진공관 시절 | 현대 |
|---|---|---|
| 스위치 | 진공관 | 트랜지스터 |
| 연산·제어·빠른 기억 | 캐비닛 여러 개 | **CPU** (ALU, FPU, 제어장치, 레지스터, 캐시) |
| 주기억장치 | 수은 지연선, 자기 드럼, 자기 코어 | DRAM (트랜지스터 1개 + 축전기 1개) |
| 장기 저장 | 천공카드, 테이프 | SSD, HDD |

| 입출력 | 카드 판독기, 텔레타이프 | 키보드, 모니터, USB, 네트워크 |

| 연결 | 케이블, 플러그 판 | 메인보드 배선, 버스 |

#### 명령이 실행되는 흐름

1. 프로그램이 저장장치에서 RAM으로 올라온다.

2. 프로그램 카운터의 주소를 주소선에 올려 RAM에서 명령(비트)을 가져온다.

3. 제어장치의 해독기가 명령을 해석해 제어 신호를 켠다.

4. ALU가 계산하고 결과를 레지스터에 저장한다.

5. 프로그램 카운터를 증가시켜 반복한다.

## 진공관 컴퓨터와 같은 점, 다른 점
- 같은 점: 0과 1, 게이트와 플립플롭, 연산·제어·기억·입출력의 구조, 프로그램을 메모리에 저장해 실행
- 다른 점: 스위치가 진공관에서 트랜지스터로 바뀌어 크기, 전력, 속도, 신뢰성이 크게 개선되었다.

**==🔴결론은 컴퓨터는 입력, 저장, 연산, 제어, 출력이 모두 0과 1로 이뤄진다. 이 원리를 알면 프로그램이 왜 그렇게 동작하는지(오류, 성능 한계 등)를 근본부터 이해할 수 있고, 문제가 생겼을 때 원인을 찾기 쉬워진다.==**

## 사람이 컴퓨터를 조작하는 방식

### 운영체제(OS)

사람은 컴퓨터의 0과 1을 직접 다루지 않고 **운영체제**를 거쳐 조작한다. OS는 하드웨어와 프로그램 사이에서 장치 제어, 메모리·파일 관리, 프로그램 실행 관리를 대신해 주는 관리자이다.

> [!info]- 화면과 입력이 처리되는 방식
> 화면은 점(픽셀)의 색을 숫자로 메모리에 써 두면, 그래픽 장치가 이를 읽어 모니터에 빛으로 표시하는 것이다.
> 키보드·마우스 입력은 비트 신호로 CPU에 전해지고(인터럽트), OS가 이를 받아 지금 선택된 프로그램에 이벤트로 전달한다.

프로그램도 하드웨어를 직접 다루지 않고 OS에 **시스템 호출**로 부탁한다. 덕분에 프로그램은 장치가 무엇이든 같은 방식으로 화면 출력, 파일 읽기 등을 할 수 있다.

## 코드가 컴퓨터로 들어가는 과정
### 기계어
CPU가 이해하는 것은 0과 1로 된 명령뿐이며, 이를 **기계어**라고 한다. 앞에서 본 것처럼 명령도 비트 패턴이고, 제어장치가 이 비트를 해독해 동작을 일으킨다.

> [!info]- 기계어의 예
> 가상의 CPU에서 "2번 레지스터 값을 더하라"는 명령이 이렇게 생겼다고 하자.
> ```
> 0001 0010
> ---- ----
> 동작  대상
> (더하기) (레지스터 2번)
> ```
> 실제 CPU도 같은 원리이며, 동작 코드와 대상을 비트로 나열한 것이다.

기계어는 CPU 종류마다 다르다. 인텔·AMD(x86)와 애플 실리콘·스마트폰(ARM)은 같은 동작도 비트 패턴이 달라서, 한 CPU용 기계어는 다른 CPU에서 실행되지 않는다.

### 사람과 기계어 사이의 간극
사람이 `1011 0000 0110 0001` 같은 비트로 프로그램을 짜는 것은 사실상 불가능하다. 그래서 사람이 읽을 수 있는 언어로 코드를 쓰고, 이를 기계어로 **번역**하는 방식이 생겼다.

| 단계 | 예 | 특징 |
|---|---|---|
| 기계어 | `0001 0010` | CPU가 바로 실행. 사람이 읽기 어려움 |
| 어셈블리어 | `ADD R2` | 기계어에 이름만 붙인 것. 기계어와 1:1 대응 |
| 고급 언어 | `c = a + b;` (Java, C, Python) | 사람이 읽기 쉬움. 한 줄이 기계어 여러 개로 번역됨 |

### 번역하는 두 가지 방법
> [!info]- 컴파일러와 인터프리터
> **컴파일러**는 코드 전체를 실행 전에 한꺼번에 번역해 기계어 파일로 만든다. 번역은 한 번만 하고, 이후에는 기계어를 바로 실행하므로 빠르다. (예: C)
>
> **인터프리터**는 실행하면서 코드를 한 줄씩 읽고 번역해 바로 실행한다. 번역 과정 없이 바로 실행해 볼 수 있어 편하지만, 매번 번역하므로 느리다. (예: 전통적인 스크립트 언어)

| | 컴파일러 | 인터프리터 |
|---|---|---|
| 번역 시점 | 실행 전, 한 번에 | 실행 중, 한 줄씩 |
| 결과물 | 기계어 파일 | 없음 (바로 실행) |
| 속도 | 빠름 | 느림 |
| 단점 | CPU·OS마다 따로 컴파일해야 함 | 매번 번역하는 비용 |

### 바이트코드와 Java의 방식
Java는 두 방법의 장점을 섞기 위해 **중간 언어**를 둔다. 이것이 **바이트코드**이며 이를 하이브리드 방식이라 하기도 한다.

- 바이트코드는 CPU가 아니라 **JVM**이 이해하는 가상의 기계어이다.
- 명령 하나가 1바이트(8비트)라서 바이트코드라고 부른다.
- CPU도 0과 1로 구성된 바이트를 읽지만 이와는 다르기에 CPU가 바이트 코드를 보고서 이해할 수는 없다. 

> [!info]- 바이트코드의 예
> `c = a + b;` 를 번역하면 대략 이렇게 된다.
> ```
> iload_1    <- a를 꺼내 쌓음
> iload_2    <- b를 꺼내 쌓음
> iadd       <- 두 값을 더함
> istore_3   <- 결과를 c에 저장
> ```
> 실제 파일 .class파일 내부에는 16진수로 작성된다


==🟡Java의 번역은 두 단계로 일어난다.==
1. **컴파일**: `javac`가 `.java` 코드를 바이트코드(`.class`)로 번역한다. (한 번)
2. **실행**: JVM이 바이트코드를 읽으며 실행한다. 이때 처음에는 인터프리터처럼 한 줄씩 실행하고, 자주 반복되는 부분은 **JIT 컴파일러**가 그 컴퓨터의 기계어로 번역해 두었다가 다음부터 빠르게 실행한다.

>[!tip]- JIT
>Just In Time &rarr; 실행 도중에 많이 사용되는 부분(핫스팟)을 기계어로 번역하여 캐시에 기록해둔다.

바이트코드를 중간에 두는 이유는 CPU마다 기계어가 다르기 때문이다. 한 번 바이트코드로 만들어 두면, 각 컴퓨터에 설치된 JVM이 그 컴퓨터의 기계어로 바꿔 주므로 같은 `.class`를 어디서나 실행할 수 있다.

### 변환 흐름
```
 Java 코드 (.java)     사람이 읽는 코드
   ↓ javac (컴파일러)
 바이트코드 (.class)    JVM이 읽는 중간 언어
   ↓ JVM (인터프리터 + JIT)
 기계어                 CPU 종류에 맞는 0과 1
   ↓
 CPU가 가져오기 → 해독 → 실행
```

## JVM
### JVM이란
JVM은 바이트코드를 실행해 주는 **프로그램**이다. 하드웨어가 아니라 OS 위에서 돌아가는 하나의 프로세스이며, OS가 JVM을 메모리에 올려 실행하면 그 안에서 우리의 코드가 돌아간다.

JVM이 있기 때문에 개발자는 CPU 종류, OS 차이, 메모리 해제를 신경 쓰지 않고 코드만 작성할 수 있다.

### 실행되기까지
1. **클래스 로더**: `.class` 파일을 필요할 때 JVM 메모리로 읽어 들인다.
2. **인터프리터**: 바이트코드를 한 줄씩 해석해 실행한다. 시작이 빠르다.
3. **JIT 컴파일러**: 자주 반복되는 부분(핫스팟)을 찾아 기계어로 미리 번역해 두고, 다음부터는 그 기계어를 바로 실행한다.

> [!info]- 왜 인터프리터와 JIT를 같이 쓰나
> 처음부터 전부 기계어로 번역하면 시작이 느리고, 전부 한 줄씩 해석하면 실행이 느리다. 그래서 처음엔 해석으로 빠르게 시작하고, 많이 쓰이는 부분만 기계어로 바꿔 속도를 높인다.

### 메모리 관리
JVM은 프로그램이 쓰는 메모리를 역할별로 나눠 관리한다.

| 영역 | 저장하는 것 |
|---|---|
| 메서드 영역 | 클래스 정보, 바이트코드 |
| 힙 | `new`로 만든 객체 |
| 스택 | 메서드 호출 정보와 지역 변수 (호출될 때 쌓이고 끝나면 사라짐) |

힙의 객체 중 더 이상 쓰지 않는 것은 **가비지 컬렉터(GC)** 가 자동으로 정리한다. C 같은 언어에서는 개발자가 직접 해야 하는 일이다.

### OS와의 관계
화면 출력이나 파일 읽기는 JVM이 직접 하드웨어를 건드리지 않고, OS에 **시스템 호출**로 부탁한다. `System.out.println("hi")`도 JVM이 OS에 "화면에 써 달라"고 요청하고, OS와 드라이버가 화면 메모리에 글자를 그린다.

## 개발 도구
### 도구 없이 실행해 보기
도구가 없다면 직접 이렇게 해야 한다.
```
javac Main.java     ← 컴파일 (Main.class 생성)
java Main           ← JVM으로 실행
```
프로그램이 커지면 파일 수백 개를 컴파일하고, 필요한 라이브러리를 직접 내려받아 연결해야 한다. 도구는 이 반복 작업을 대신해 준다.

### IDE
IntelliJ 같은 **IDE**는 코드 작성부터 실행까지 한곳에서 처리한다.
- 문법 오류를 쓰는 즉시 표시하고, 자동완성을 제공한다.
- 실행 버튼 하나로 컴파일(javac)과 실행(JVM)을 대신 호출한다.
- 실행을 멈추고 변수 값을 보는 디버깅 기능을 제공한다.

### 빌드 도구와 라이브러리
**Gradle, Maven** 같은 빌드 도구가 프로젝트 관리를 맡는다.
- 필요한 **라이브러리**를 설정 파일에 적으면 자동으로 내려받아 연결한다.
- 컴파일 순서를 관리하고, 테스트를 실행하고, 결과를 **JAR**(`.class` 파일들을 묶은 압축 파일)로 포장한다.

## 프레임워크
**프레임워크**는 서버, DB 연결처럼 거의 모든 프로그램에 필요한 기본 틀을 미리 만들어 둔 코드 묶음이다. 개발자는 그 틀 위에 자기 로직만 채운다.

>[!warning]- 프레임워크는 개발환경인가요?
>라고 생각한다면 나와 동일한 사람
>프레임워크라는 말을 들으면 IDE 대신 사용하는 공간, 정해진 틀 속에서 작업을 도와주는 프로그램이라고 생각하기 쉽다.
>본인도 스프링이 프레임워크라고 할 때 그렇게 생각했었다.
>==🔵따라서 정답은==
>프레임워크는 작업 공간이 아니라, 어떤 목적에 필요한 문제 해결 방법을 모아둔 **코드의 뼈대**이다.
>공통되는 부분(서버 실행, 요청 처리 등)은 프레임워크가 맡고, 우리는 그 뼈대 안에서 프로그램만의 로직을 채운다.
>==그럼 라이브러리 아닌가요?==
>둘 다 코드의 묶음이지만 **누가 흐름을 쥐고 있는가**가 다르다.
>라이브러리는 내 코드가 흐름을 쥐고 필요할 때 라이브러리를 호출해 쓴다.
>프레임워크는 프레임워크가 흐름을 쥐고 필요한 때에 내가 작성한 코드를 호출한다. (제어의 역전)
>프레임워크도 JAR로 배포되는 코드라서, 빌드 도구가 내려받아 내 코드와 함께 JVM에서 실행된다.

Spring Boot는 예를 들어 이런 일을 대신한다.
- 웹 서버(톰캣)를 내장해서 직접 설치하지 않아도 서버가 실행된다.
- 객체를 만들고 서로 연결하는 일(의존성 주입)을 자동으로 처리한다.
- 자주 쓰는 설정을 기본값으로 채워 준다.

## 정리
코드가 실행되기까지는 여러 층을 거치며, 각 층은 아래층의 복잡함을 감춰 준다.

| 층 | 감춰 주는 것 |
|---|---|
| 프레임워크 | 서버·설정 같은 반복되는 기본 틀 |
| 빌드 도구 | 라이브러리 관리, 컴파일 순서, 포장 |
| IDE | 컴파일·실행 명령, 오류 찾기 |
| javac와 JVM | CPU별 기계어, 메모리 해제 |
| OS | 장치 제어, 프로그램 간 충돌 방지 |
| 하드웨어 | 게이트와 플립플롭 = 0과 1 |


# 결론
컴퓨터는 0과 1로 이루어져 있고, 사용 방식은 시대에 따라 도구들이 각 단계를 대신해 주는 방향으로 발전해 왔다. 컴퓨터를 사용하는 흐름에서 어떤 부분을 도구가 대신하고 어떤 부분을 우리가 해야 하는지 알면, 개발할 때 문제가 생겨도 원인이 되는 단계를 찾을 수 있다.

## 레거시 방식
- ENIAC 시대 : 케이블 배선, 스위치로 프로그램 구성 -> 실행
- 프로그램 내장 초기 : 기계어(0과 1) 직접 작성 (천공카드 등으로 입력) -> 메모리에 입력 -> CPU 실행
- 어셈블리 시대 : 어셈블리어 작성 -> 어셈블러가 기계어로 번역 -> 메모리에 로드 -> CPU 실행
- 컴파일러 시대 : FORTRAN, C와 같은 고급 언어 작성(천공카드, 터미널) -> 컴파일러가 기계어로 번역 -> OS가 로드 -> CPU 실행
- 초기의 자바 : 텍스트 편집기로 .java 작성 -> javac(.class 생성) -> java(JVM) -> CPU 실행

## 현대의 방식
IDE -> 프로젝트 준비(빌드 도구, 라이브러리, 프레임워크) -> 코드 작성(.java) -> 빌드(javac로 .class 생성) -> JVM(기계어로 번역) -> CPU 실행

예전에는 번역, 메모리 입력, 장치 제어까지 대부분을 직접 해야 했다면, 현대에는 IDE, 빌드 도구, 프레임워크, JVM, OS가 그 단계를 대신해 주기 때문에 우리는 서비스의 로직을 작성하는 데 집중할 수 있다.
