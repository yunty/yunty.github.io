## 세부 내용
- 리플렉션
  - 실행 중에 클래스, 메서드, 필드 정보를 읽고 호출하는 기능
  - 프레임워크는 내가 만들 클래스를 코드에 적을 수 없으니, 클래스 파일 경로를 훑어 이름을 알아내고 리플렉션으로 다룸 (컴포넌트 스캔)
  - 스프링 : 빈 생성(`newInstance`), 생성자 파라미터 타입으로 DI, `method.invoke(bean, args)`로 컨트롤러 실행
- 어노테이션
  - 코드에 붙이는 꼬리표. **스스로는 동작 안 함**, 읽는 쪽이 처리함
  - `@Retention` 으로 남는 범위 결정 : SOURCE(컴파일러, Lombok) / CLASS / RUNTIME(스프링)
  - 직접 만들 땐 `@interface`, 읽는 코드는 따로 작성
- 패턴 매칭
  - 타입 검사 + 캐스팅 + 변수 선언을 한 번에 (`obj instanceof Point(int x, int y)`)
  - 겉 타입(Object)과 실제 타입이 달라서 검사가 필요한 것
- sealed
  - `permits`로 상속 가능한 클래스를 제한, 하위는 `final` / `sealed` / `non-sealed`
  - switch 패턴 매칭과 같이 쓰면 `default` 없이도 누락을 컴파일러가 검사
  - 종류가 고정 상수이면 enum (상수별 값, 메서드도 가능), 종류마다 필드 모양이 다르고 값마다 객체를 만들면 sealed + record
- 중첩 클래스
  - static 중첩 / 내부 / 지역 / 익명 4가지
  - 내부 클래스는 바깥 객체 참조를 숨겨서 들고 있음 → 메모리 누수 가능, 바깥 필드가 필요 없으면 static이 기본
  - 실무 : DTO, enum, 빌더, 테스트 설정 등 그 클래스 전용의 작은 타입

## 헷갈렸던 것 / 질문
%%  풀렸으면 success, 아직 헷갈리면 warning. 제목(Q)만 보고 답을 먼저 떠올린 뒤 펼쳐서 확인하기 %%
> [!success]- Q. 어노테이션은 리플렉션 없이는 못 읽나?
> 아니다. 컴파일 때는 어노테이션 프로세서(Lombok), `.class` 파일을 직접 읽는 바이트코드 방식(스프링 스캔), 실행 중에는 리플렉션으로 읽는다. 어디까지 남을지는 `@Retention`이 정한다.

> [!success]- Q. 레코드 패턴에서 내부적으로 왜 타입 검사를 하나?
> getter는 타입을 알 때만 쓸 수 있다. `Object`처럼 상위 타입으로 받은 값은 실제로 Point인지 확인해야 `x()`를 부를 수 있어서, 확인과 꺼내기를 한 번에 해주는 것.

> [!success]- Q. enum이 있는데 sealed + 스위치 패턴매칭은 왜 쓰나?
> enum도 상수마다 값(생성자)과 메서드를 다르게 줄 수 있고, 상수별 메서드(다형성)로 switch 없이 처리할 수도 있다. 차이는 **인스턴스**다. enum은 선언한 상수가 프로그램에 딱 하나씩이고 필드 모양이 모두 같다. sealed + record는 종류마다 필드 모양이 다르고, 실행 중에 값마다 객체를 계속 만들 수 있다 (예: 결제 요청마다 다른 카드번호).

> [!success]- Q. static 중첩은 바깥 인스턴스 필드를 못 쓰는데 왜 만드나?
> 새 능력이 아니라 정리 목적이다. 이름 소속 표시, `private`으로 외부 숨김, 서로의 `private` 접근, 숨은 참조가 없어 메모리 누수 위험이 없음.
