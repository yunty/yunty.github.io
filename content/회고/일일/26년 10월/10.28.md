## 세부 내용
 스프링 DB 접근 기술**
- 순수 JDBC
  - 의존성: `spring-boot-starter-jdbc` + `runtimeOnly h2`
  - `application.properties`에 url / driver-class-name / username 설정 (부트 2.4부터 `username=sa` 필수, 끝에 공백 있으면 오류)
  - `DataSource`를 생성자로 주입받아 `Connection → PreparedStatement → ResultSet` 직접 다루고 `finally`에서 직접 close (반복 코드 많음, "참고만")
  - 커넥션은 `DataSourceUtils.getConnection(dataSource)`로 얻고 `DataSourceUtils.releaseConnection`으로 반납 (트랜잭션 동기화 유지 목적)
  - 스프링 부트가 접속 정보로 `DataSource`를 만들어 빈으로 등록해둬서 DI 가능
- OCP: 설정(`SpringConfig`)의 `@Bean` 반환 한 줄만 바꿔 구현체 교체 (Memory → Jdbc → JdbcTemplate → Jpa), 기존 코드는 수정 X
- 스프링 통합 테스트: `@SpringBootTest`(컨테이너+DB 같이 실행) + `@Transactional`(테스트 시작 전 트랜잭션 시작, 끝나면 항상 롤백 → 데이터 안 남음)
- JdbcTemplate: JDBC 반복 코드(커넥션, close, 예외 변환) 제거, SQL은 직접 작성. `RowMapper`로 결과 매핑, `SimpleJdbcInsert`로 insert
- JPA
  - SQL까지 JPA가 만들어서 실행, SQL 중심 → 객체 중심 설계
  - 의존성 `spring-boot-starter-data-jpa` (jdbc 포함이라 jdbc 제거 가능)
  - 설정: `spring.jpa.show-sql=true`(SQL 출력), `spring.jpa.hibernate.ddl-auto=none`(테이블 자동생성 끔, `create`면 엔티티로 생성)
  - 엔티티: `@Entity`, `@Id @GeneratedValue(strategy = IDENTITY)`. 부트 3.0+는 `javax.persistence` → `jakarta.persistence` (단 `javax.sql.DataSource`는 그대로)
  - `EntityManager`로 `persist` / `find` / `createQuery`(JPQL). `:name` 파라미터는 `setParameter`로 바인딩
  - **JPA의 모든 데이터 변경은 트랜잭션 안에서** → 서비스에 `@Transactional` (정상 종료 시 커밋, 런타임 예외 시 롤백)
- 스프링 데이터 JPA: `JpaRepository<Member, Long>`를 상속한 인터페이스만 만들면 구현체 없이 CRUD, 메서드 이름 조회(`findByName`), 페이징 제공. 스프링이 빈으로 자동 등록. JPA를 먼저 학습한 뒤 볼 것
- 실무: JPA + 스프링 데이터 JPA가 기본, 복잡한 동적 쿼리는 Querydsl, 그래도 안 되면 네이티브 쿼리 / JdbcTemplate

**7. AOP**
- 문제: `join()`, `findMembers()`마다 시간 측정 코드를 넣으면 핵심 로직과 공통 로직이 섞이고, 변경 시 전부 찾아 고쳐야 함
- 핵심 관심 사항(core concern, 비즈니스 로직) vs 공통 관심 사항(cross-cutting concern, 시간 측정 등)을 분리하는 것이 AOP (Aspect Oriented Programming)
- 적용: `@Aspect` + `@Component`, `@Around("execution(* hello.hellospring..*(..))")`, `joinPoint.proceed()` 앞뒤로 시간 측정 (`@Component` 대신 `@Bean`으로 등록해도 됨)
- 효과: 공통 로직을 한 곳에서 관리, 핵심 로직 깔끔, 적용 대상을 패턴으로 선택 가능
- 동작 방식: AOP 적용 시 스프링이 **프록시**(가짜 서비스)를 먼저 만들어 주입 → `컨트롤러 → 프록시 → proceed() → 실제 서비스` 순으로 호출. 콘솔에서 `$$EnhancerBySpringCGLIB`로 프록시 주입 확인

## 헷갈렸던 것 / 질문
%%  풀렸으면 success, 아직 헷갈리면 warning. 제목(Q)만 보고 답을 먼저 떠올린 뒤 펼쳐서 확인하기 %%
> [!success]- Q. 컴포넌트 스캔(`@Service` + `@Autowired`)을 그대로 두고 `@Configuration`으로도 등록하면 어느 쪽이 우선인가?
> 우선순위가 아니라 **이중 등록**이 된다. 빈 이름이 다르면 같은 타입 빈이 2개라 주입 시 `NoUniqueBeanDefinitionException`, 이름이 같으면 부트 2.1+에서 `BeanDefinitionOverrideException`(순수 스프링은 나중에 등록된 `@Bean`이 덮어씀). `@Bean`으로 등록할 클래스에는 `@Service`/`@Repository`를 붙이지 않는다. `@Controller`는 스캔에 맡기고 `@Autowired`로 주입받는다.

> [!success]- Q. 통합 테스트가 성공하는데 왜 DB에 반영이 안 되나?
> 테스트의 `@Transactional`은 끝나면 **자동 롤백**한다. 남기고 싶으면 `@Commit` / `@Rollback(false)`. 단, 데이터가 쌓여 다음 실행 때 중복 회원 예외가 날 수 있다.

> [!success]- Q. `@SpringBootTest`가 `initializationError`로 실패하거나 설정을 못 찾는 이유는?
> `@SpringBootTest`는 테스트 패키지에서 **위로 올라가며** `@SpringBootApplication` 클래스를 찾는다. 테스트가 `com.service`에 있고 앱이 `com.example.demo`에 있으면 못 찾으므로 앱 패키지 아래로 옮긴다. 순수 단위 테스트(`MemberServiceTest`)는 스프링을 안 쓰니 위치와 무관하다.

> [!success]- Q. 생성자 주입이란? `DataSource`를 왜 주입받나?
> 필요한 객체를 `new`로 직접 만들지 않고 생성자 파라미터로 받는 것. 구현체 교체가 쉽고 `final`을 쓸 수 있고 테스트하기 좋다. `DataSource`는 DB 연결을 얻는 입구라서, 리포지토리는 접속 정보를 모른 채 `getConnection()`으로 연결만 빌려 쓴다. `AppConfig`(`@Configuration`)는 컨테이너에서 `DataSource`를 받아 `new JdbcMemberRepository(dataSource)`로 **전달하는 조립자**다.

> [!success]- Q. `DataSource`와 커넥션 풀의 관계는? 어디에 있나?
> `HikariDataSource`가 설정(url, 계정 등)과 `HikariPool`을 필드로 가진다. 풀 안에는 DB와 이미 이어진 실제 `Connection`들이 있고, 각각 TCP 소켓을 쥐고 있다. 자바 객체는 앱 서버 JVM 힙에, 소켓은 OS 커널(파일 디스크립터와 버퍼)에, DB 쪽에는 세션이 따로 잡힌다. 앱 시작 시 미리 연결을 만들어 두고(기본 `minimum-idle`은 풀 크기와 같음), idle timeout / max lifetime으로 관리한다.

> [!success]- Q. `close()`를 하면 연결이 끊기나?
> 아니다. 풀이 주는 `Connection`은 진짜 연결을 감싼 **프록시**라서 `close()`가 "풀에 반납"으로 동작한다. 반납을 안 하면 풀이 고갈된다. (AOP의 프록시와 같은 발상)

> [!success]- Q. JPQL에서 `:name`은 무엇이고 꼭 `name`이어야 하나?
> JDBC의 `?` 대신 쓰는 **이름 기반 파라미터 바인딩**. 콜론만 필수이고 뒤의 이름은 자유(`m.name`의 필드명과 우연히 같을 뿐). `setParameter("name", 값)`으로 채우며, 값이 쿼리 구조가 아니라 데이터로 전달되어 SQL 인젝션을 막는다.
