## 세부 내용
- 실습 환경
  - `Building REST services with Spring` 가이드, Gradle, Spring Boot 4.0.0 (가이드는 Maven 기준이라 직접 옮겨서 진행)
- 클래스별 역할
  - Entity(Employee) : 식별자를 가진 객체로 DB 한 행을 표현
  - Repository(EmployeeRepository) : `JpaRepository`를 상속한 **인터페이스**, 구현체는 실행 시점에 스프링이 만들어 줌
  - Configuration(LoadDatabase) : 빈을 등록하는 설정 클래스, 앱 시작 시 샘플 데이터를 저장하는 `CommandLineRunner` 빈을 등록
  - Controller(EmployeeController) : HTTP 요청을 받아 Repository로 Entity를 다루고 응답
  - Exception(EmployeeNotFoundException) : 직원을 못 찾았을 때 던지는 예외
  - Advice(EmployeeNotFoundAdvice) : 그 예외를 잡아 404와 메시지로 바꿔 응답
- 실행 경로
  - 시작 : 컨테이너가 빈 등록 → LoadDatabase → Repository.save() → DB에 샘플 데이터
  - 요청 : Tomcat → DispatcherServlet → Controller → Repository → DB → Employee → JSON 변환 → 응답
  - 예외 : Controller에서 예외 발생 → Advice가 받아 404 응답
- 엔티티와 도메인
  - 엔티티 : 테이블 = 클래스, 행 = 객체, 열 = 필드, 기본키(id)로 구분되는 객체 (필드값 하나가 아니라 한 행 전체)
  - 도메인 : 해결하려는 문제 영역. 엔티티는 도메인 객체의 한 종류 (값 객체, 도메인 서비스도 있음)
  - 엔티티도 책임을 가질 수 있음 (예: `order.cancel()`), 규칙을 서비스에만 두면 빈약한 도메인 모델
  - 애그리게이트 루트 : 연관된 객체 묶음의 대표이자 진입점. 가이드에서는 `/employees`(전체 목록의 시작 주소)를 느슨하게 가리킴
- Gradle 의존성 추가
  - 의존성 = 내 프로젝트가 쓰는 외부 라이브러리. 빌드 파일에 적으면 Gradle이 저장소에서 JAR를 내려받아(필요한 다른 라이브러리까지) 클래스 경로에 연결
  - `implementation 'org.springframework.boot:spring-boot-starter-hateoas'` (버전은 부트가 맞춰 주므로 생략), 테스트용은 `testImplementation ...starter-hateoas-test`
  - Boot 4는 `starter-web`이 `starter-webmvc`로 바뀌는 등 이름이 가이드와 다름
  - 적용 : IntelliJ의 Load Gradle Changes 또는 `./gradlew build`
- HATEOAS
  - HATEOAS는 REST의 원칙(개념), Spring HATEOAS는 그 개념을 쓰게 해 주는 라이브러리, `spring-boot-starter-hateoas`는 의존성 묶음
  - 응답에 다음에 할 수 있는 동작의 링크를 함께 담음. 링크 = URI + rel(관계 이름: self, employees)
  - HAL : JSON에 링크를 `_links`로 담는 약속된 형식(mediatype)
  - 이유 : 서버가 링크를 추가하거나 주소를 옮겨도 옛 클라이언트는 기존 링크로 계속 동작 (변경에 강함). 현실에서는 응답이 커져서 선택적으로 씀
  - 링크를 담는 상자 : `RepresentationModel`(부모) → `EntityModel<T>`(단건) / `CollectionModel<T>`(목록 + 목록 자체의 링크) / `PagedModel<T>`(페이지)
  - `linkTo(methodOn(EmployeeController.class).one(id))` : 컨트롤러 메서드를 가리켜 주소를 계산 (메서드는 실행되지 않음), 매핑 주소가 바뀌어도 자동으로 따라감
  - 목록 응답 : 항목들은 `_embedded.employeeList`, 목록 전체의 링크는 바깥 `_links.self`
  - 100만 건을 한 번에 주면 안 됨 → 페이지 처리(`Pageable`)와 `next`/`prev` 링크
- 링크 생성 중복 제거
  - `EmployeeModelAssembler`(`RepresentationModelAssembler` 구현, `@Component`)의 `toModel()`로 "직원 → 링크 달린 `EntityModel`" 변환을 한 곳에 모음
  - 컨트롤러는 `assembler.toModel(employee)`, 목록은 `.map(assembler::toModel)`
- 도구
  - `curl`로 HTTP 요청, `| json_pp`로 JSON을 보기 좋게 정리 (Curling prettier)

## 헷갈렸던 것 / 질문
%%  풀렸으면 success, 아직 헷갈리면 warning. 제목(Q)만 보고 답을 먼저 떠올린 뒤 펼쳐서 확인하기 %%
> [!success]- Q. 엔티티는 객체가 아니라 DB의 필드값을 가리키는 말인가?
> 필드값 하나가 아니라 DB 한 행을 표현하는 객체다. 테이블은 클래스, 행은 객체, 열은 필드에 대응하고 id(기본키)로 구분한다.

> [!success]- Q. 지뢰찾기의 셀 객체처럼 책임을 가진 객체와 엔티티는 다른 것인가?
> 같은 뿌리다. 책임 중심 객체는 규칙을 맡기려고 만들고, JPA 엔티티는 객체를 DB 행과 연결하려고 만든다. 엔티티도 `cancel()` 같은 책임을 가질 수 있다.

> [!success]- Q. 도메인은 엔티티를 의미하나?
> 아니다. 도메인은 해결하려는 업무 영역이고, 엔티티는 그 영역을 표현하는 도메인 객체 중 식별자를 가진 종류다. 스프링 강의에서 `domain` 패키지에 엔티티가 들어 있어 같은 뜻처럼 쓰이는 것이다.

> [!success]- Q. 애그리게이트 루트는 무엇인가?
> 연관된 객체 묶음의 대표이자 진입점이다(예: 주문과 주문 항목에서 주문). 가이드에서는 느슨하게 `/employees` 같은 전체 목록의 시작 주소를 가리킨다.

> [!success]- Q. HATEOAS는 라이브러리인가?
> HATEOAS는 REST의 원칙(개념)이고, Spring HATEOAS가 그 개념을 쓰게 해 주는 라이브러리다. `spring-boot-starter-hateoas`는 그 라이브러리와 설정을 가져오는 의존성 묶음이다.

> [!success]- Q. 목록 응답의 "캡슐화"는 EntityModel로 각 직원의 링크를 만드는 것인가?
> 두 겹이다. `EntityModel`은 직원 한 명과 그 링크를 감싸고, `CollectionModel`은 그 목록을 목록 자체의 링크와 함께 한 번 더 감싼다. 가이드의 "컬렉션 캡슐화"는 바깥 상자인 `CollectionModel`을 가리킨다.

> [!success]- Q. 링크를 다 붙이면 응답이 너무 커지지 않나? (100만 건이면?)
> 커진다. 그래서 목록은 한 번에 주지 않고 `Pageable`로 나누며, 페이지 이동 링크(`next`, `prev`)를 `PagedModel`이 담는다. 링크가 주는 이점 대신 크기가 늘어나서 실무에서는 선택적으로 쓴다.

> [!success]- Q. 링크를 담는 건 EntityModel뿐인가?
> 아니다. 부모 `RepresentationModel` 아래에 `EntityModel`(단건), `CollectionModel`(목록), `PagedModel`(페이지)이 있고, 링크 붙이는 일을 맡기는 `RepresentationModelAssembler`도 있다.

> [!success]- Q. 의존성을 추가한다는 게 무엇인가?
> 내 코드가 쓰는 외부 라이브러리를 빌드 파일에 적어서, Gradle이 JAR를 내려받아 프로젝트에 연결하게 하는 것이다.
