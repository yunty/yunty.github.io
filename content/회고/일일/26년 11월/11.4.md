## 세부 내용
- 역할과 구현, 인터페이스를 통해 역할을 정의
- 구체를 의존하기보단 추상을 의존하자
- 정적인 클래스 의존관계보단 동적인 객체 인스턴스 의존 관계
- AppConfig 혹은 Assembler 등의 역할을 IoC컨테이너 혹은 DI컨테이너라고 한다.
- 스프링 컨테이너의 최상위 인터페이스 : BeanFactory
	- 빈을 관리하고 조회하는 역할
	- getBean()을 제공해준다.
	- 스프링 빈의 메타정보 : BeanDefinition
		- getBean(빈이름, 타입(.class))로 등록된 빈 조회 가능
			- 없을 시 NoSuchBeanDefinitionException 예외 발생
		- 부모 타입으로 조회 시에는 자식타입까지 조회
	- ApplicationContext(자식 인터페이스 이며 여러 구현체를 가지고 잇음)
		- BeanFactory의 빈 관리, 조회 + 부가기능이 포함된 인터페이스
- 빈 이름은 항상 다른 이름을 부여 겹칠 시 스프링 프레임워크에서는 수동 등록이 자동 등록을 오버라이딩, 스프링 부트에서는 예외발생
	- 물론 자동으로 설정해두는 빈들이 중복될 시 `ConfilictingBeanDefinitionException` 예외 발생
- 스프링은 빈으로 등록되는 객체들을 프록시 객체를 생성하여 등록하게 되며 이를 통해 싱글톤 패턴을 자동으로 적용해준다.
- 즉 스프링 컨테이너가 싱글톤 컨테이너 역할을 한다.
- 따라서 빈은 싱글톤 패턴으로 사용되기 위해서는 무상태로 설계해야한다
	- 클라이언트 의존 필드 x
	- 지역변수, 파라미터 등을 사용하여 공유 되는 필드가 없도록 한다.
- 컴포넌트 스캔을 통해 기존 @Configuration 에노테이션을 달고 @Bean을 하나하나 설정하던것과는 다르게 자동으로 @Component로 설정해둔것들을 빈으로 등록해주며 생성자 자동주입을 해준다.(2개 이상부터는 @Autowired)
	- @Configuration도 사실 @Component 에노테이션을 포함하기에 스캔된다.
- 스캔 범위는 별도의 basePackages, basePackageClasses등으로 설정하지 않는다면 기본 디폴드 값이 @ComponentScan이 붙은 설정 정보 클래스의 패키지와 그 하위 패키지를 스캔한다.
- @ComponenetScan(여기) 안에 includeFilters, excludeFilters 옵션을 넣어서 스캔 대상을 추가하거나 제외할 수 있다.

> [!success]- Q. excludeFilters의 값으로 에노테이션(@Filter)이 왜 들어가는가
> `excludeFilters`의 타입이 `Filter[]`(어노테이션 배열)이기 때문이다. 제외 조건 하나가 `type`과 `classes` 두 정보로 이루어지는데, 이 묶음을 담는 그릇이 `@Filter`다. 객체를 `new Filter(type, classes)`로 넘기는 대신 어노테이션 문법으로 설정 묶음을 선언한 것이다. 값은 컴파일 시점에 정해지는 상수(문자열, 클래스 리터럴, enum, 어노테이션)만 가능하다.
>
> ```java
> @ComponentScan(
>     excludeFilters = {
>         @Filter(type = FilterType.ANNOTATION, classes = Configuration.class),
>         @Filter(type = FilterType.ANNOTATION, classes = MyExclude.class)
>     })
> ```

> [!success]- Q. 컴포넌트 스캔을 서로 다른 패키지에 하나씩 두면 어떻게 되는가?
> 스캔은 설정 클래스마다 독립적으로 돌고, 결과는 한 컨테이너에 합쳐진다. 두 설정 클래스가 같은 컨텍스트에 등록돼야 한다(둘 다 넘기거나 `@Import`). 범위가 겹쳐도 같은 빈 이름이면 한 번만 등록된다. 다른 클래스가 같은 이름이면 `ConflictingBeanDefinitionException`, 같은 타입 빈이 둘이면 주입 때 `NoUniqueBeanDefinitionException`이 난다. 실무에서는 루트 패키지에 `@SpringBootApplication` 하나를 둔다.

> [!success]- Q. @Controller, @Service 같은 걸 굳이 만든 이유는? 상속인가, 편의인가?
>  자바 어노테이션은 상속이 없다. `@Controller`, `@Service`, `@Repository`의 정의 안에 `@Component`가 붙어 있고(메타 어노테이션), 스프링이 이를 타고 올라가서 `@Component`로 인식한다. 이유는 두 가지다. 첫째, 계층의 역할을 이름으로 드러내 읽기 쉽게 한다. 둘째, 일부는 실제 기능이 다르다. `@Controller`는 MVC가 핸들러 매핑 대상으로 인식하고, `@Repository`는 DB 예외를 스프링 예외로 변환한다. `@Service`는 추가 기능 없이 의미 표시다.
