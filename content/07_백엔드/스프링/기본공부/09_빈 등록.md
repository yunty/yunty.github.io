# 빈 등록

---
## 빈이란
- 스프링 컨테이너가 **만들고 관리하는 객체**
- 내가 `new`로 만든 객체는 그냥 자바 객체이고, 컨테이너가 받아서 관리해야 빈이 됨
- 기본은 **싱글톤** : 컨테이너가 하나만 만들어서 공유 (싱글톤 레지스트리)
	- 그래서 빈은 **무상태**로 설계. 공유 필드에 값을 쓰면 요청끼리 섞임

## 등록 과정
1. 컨테이너를 만들 때 설정 정보를 넘김 (`AppConfig.class` 등)
2. 컨테이너가 설정 정보를 읽어서 **BeanDefinition**(빈 설정 메타정보)을 만듦
3. 그 정보를 바탕으로 빈 객체를 만들어서 보관
- 설정이 자바 코드든 XML이든 BeanDefinition으로 통일돼서 컨테이너는 형식을 몰라도 됨

---
## 등록 방법 2가지
| | 컴포넌트 스캔 | `@Configuration` + `@Bean` |
|---|---|---|
| 방식 | 클래스에 `@Component`를 붙이면 자동 등록 | 설정 클래스에서 직접 `new`해서 반환 |
| 빈 이름 | 클래스명 앞글자 소문자 (`memberServiceImpl`) | 메서드 이름 |
| 잘 맞는 곳 | 내가 만든 대부분의 클래스 | 외부 라이브러리 클래스, 구현체를 한 곳에서 바꾸고 싶을 때 |

### 컴포넌트 스캔
- `@Controller`, `@Service`, `@Repository`, `@Configuration`은 모두 `@Component`를 포함해서 같이 스캔됨
	- 어노테이션 상속이 아니라 스프링이 안에 든 걸 인식해주는 것
	- `@Controller`(MVC 컨트롤러로 인식), `@Repository`(데이터 예외 변환)는 부가 기능이 있고, `@Service`는 의미 표시
- **스캔 범위** : `@ComponentScan`이 붙은 클래스의 패키지와 그 하위
	- 그래서 설정 클래스를 프로젝트 **루트 패키지**에 두는 게 권장 (`@SpringBootApplication`도 같은 이유)
- 필터로 대상을 추가/제외할 수 있지만 거의 안 씀 (`includeFilters`, `excludeFilters`)

### `@Bean`
- `@Configuration`을 꼭 붙이자 → 붙어 있어야 `@Bean` 메서드를 여러 번 호출해도 싱글톤이 보장됨
	- 스프링이 `@Configuration` 클래스를 바이트코드 조작(CGLIB)으로 상속한 클래스로 바꿔서 이미 있는 빈을 반환하게 해줌

---
## 주의 : 중복
| 상황 | 결과 |
|---|---|
| 한 클래스를 `@Component`와 `@Bean`으로 둘 다 등록 | 빈이 2개 (이름이 같으면 충돌) |
| 자동 등록끼리 이름이 같음 | `ConflictingBeanDefinitionException` |
| 수동 vs 자동 이름 충돌 | 스프링은 수동 우선, **스프링 부트는 오류** |
- 클래스마다 **한 가지 방식으로만** 등록하면 두 방식을 섞어 써도 문제 없음
- 같은 타입이 여러 개 등록되는 것 자체는 문제가 아님. 하나로 받으려 할 때(주입 시점) 오류 → [[10_의존관계 주입|의존관계 주입]]

## 한 줄 정리
- 빈 등록 = 컨테이너가 객체를 만들어 관리 아래에 두는 것
- 기본은 컴포넌트 스캔, 스캔이 못 닿는 것과 직접 조립하고 싶은 것은 `@Bean`
