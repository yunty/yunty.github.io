# 의존관계 주입

---
## DI란
- 필요한 객체를 내가 `new`하지 않고 **외부(컨테이너)가 넣어주는 것**
- 왜 필요한가
	- 구현체를 직접 `new`하면 구체 클래스에 의존하게 돼서 DIP/OCP가 깨짐
	- 인터페이스(추상)에만 의존하고, 어떤 구현이 들어올지는 외부가 정함 → 구현을 바꿔도 사용하는 코드는 그대로
- 이걸 해주는 게 IoC/DI 컨테이너 (AppConfig, 스프링 컨테이너)

| 의존관계 | 설명 |
|---|---|
| 정적 | `import`만 보고 알 수 있음. 클래스 다이어그램 |
| 동적 | 실행 시점에 실제로 연결된 객체. 주입으로 바뀜 |
- 주입을 쓰면 정적 의존관계는 그대로 두고 동적 의존관계만 바꿀 수 있음

---
## 주입 방법
| 방법 | 시점 | 특징 |
|---|---|---|
| **생성자 주입** | 객체 생성과 동시 | 기본으로 쓰는 방식 |
| 수정자(setter) 주입 | 생성 후 | 선택적 의존관계에 가끔 |
| 필드 주입 | 생성 후 | 테스트하기 어려워서 비추천 |

- 생성자 주입이 기본인 이유
	- 필수 의존관계가 없으면 아예 생성이 안 되니 **불완전한 객체가 없음**
	- `final`을 쓸 수 있어서 한 번 정해지면 안 바뀜
- 생성자가 **1개**면 `@Autowired` 생략 가능, 2개 이상이면 주입할 생성자에 붙임
- 주입받는 쪽도 빈이어야 하고, **주입되는 것도 빈**이어야 함 (`new`한 객체는 못 넣음)

---
## 주입 규칙
- 기본은 **타입으로** 빈을 찾아서 넣음 (`getBean(타입)`과 비슷)
- 같은 타입의 빈이 여러 개면 하나로 받을 때 `NoUniqueBeanDefinitionException`
	- 등록이 문제인 게 아니라 **주입 시점**에 못 고르는 것

| 해결 | 방법 |
|---|---|
| 기본값 지정 | 구현 쪽에 `@Primary` |
| 이름표로 지정 | 받는 쪽에 `@Qualifier("이름")` |
| 하나만 등록 | 쓸 구현에만 `@Component` |
| 전부 받기 | `List`, `Map`으로 받아서 코드에서 선택 |

- `Map<String, 타입>`은 키가 **빈 이름**. 골라 쓰면 전략 패턴이 됨
- `List`/`Map` 자체는 빈이 아니라 스프링이 주입할 때 모아서 만들어주는 임시 컬렉션 (안에 든 건 원래 빈)

## 주입 중 예외가 나면
- 생성자 주입이면 재료가 없을 때 **객체 자체가 안 만들어짐**
- 싱글톤 빈은 컨테이너 시작 때 만들어서 하나라도 실패하면 **컨테이너 생성이 실패**
	- 예) 스캔 범위 밖이라 `MemberRepository`를 못 찾으면 `UnsatisfiedDependencyException`

---
## 한 줄 정리
- DI = 구현을 `new`하지 않고 컨테이너가 넣어줌 → 추상에만 의존할 수 있음
- 기본은 생성자 주입, 같은 타입이 여럿이면 `@Primary`/`@Qualifier`/`List`·`Map`
