# 빈과 의존관계

---
## 스프링 컨테이너와 빈
- 스프링 컨테이너 : 객체(빈)를 만들고, 관리하고, 연결해주는 곳
- 빈 : 컨테이너가 관리하는 객체. 기본은 **싱글톤**
- 내가 `new`로 만들지 않고 컨테이너가 필요한 곳에 넣어줌 → **DI**(의존성 주입)

## 계층 구조 (회원 관리 예제)
```
컨트롤러 → 서비스 → 리포지토리 → 도메인
```
| 계층 | 역할 |
|---|---|
| 컨트롤러 | 웹 요청을 받아서 서비스로 넘김 |
| 서비스 | 비즈니스 규칙 (가입, 조회) |
| 리포지토리 | 저장소 접근 |
| 도메인 | 비즈니스에서 다루는 대상 (Member) |

- 의존 방향은 한쪽으로만
- 저장소가 아직 안 정해졌다고 가정하고 **인터페이스(MemberRepository)로 설계** → 구현체를 갈아끼우기 쉬움

---
## 빈 등록 방법 2가지
**1. 컴포넌트 스캔 + 자동 의존관계**
- `@Controller`, `@Service`, `@Repository`가 붙으면 자동 등록 (전부 `@Component`를 포함)
- 의존관계는 생성자에 `@Autowired` (생성자가 1개면 생략 가능)

**2. 자바 코드로 직접**
- `@Configuration` + `@Bean`으로 `new`를 직접 해서 넣어줌
- 구현체를 바꿀 때 설정만 고치면 돼서 편함

---
## 알게 된 점
- 컴포넌트 스캔은 **빈 등록**까지. 의존관계 연결은 `@Autowired`(생성자 주입)가 함
- 스캔 범위는 `@SpringBootApplication`이 붙은 클래스의 패키지 + 그 하위 (같은 패키지만 X)
- 같은 클래스를 두 방식으로 같이 등록하면 빈이 2개가 돼서 주입할 때 에러
- DI는 생성자 주입이 기본 (`final`을 쓸 수 있고 테스트하기 좋음)

## 웹 MVC (폼 데이터)
- html의 input `name` = 폼 객체의 필드 이름 → 스프링이 객체를 만들어서 setter로 채워줌
- 컨트롤러가 폼 객체를 도메인 객체로 바꿔서 서비스에 넘김 (서비스는 웹 객체를 몰라야 하니깐)
- 컨트롤러가 정적 파일보다 우선순위가 높음
