# DB 접근 기술
구현체만 갈아끼우면서 DB랑 소통하는 방법을 바꿔봄

```
메모리 → 순수 JDBC → JdbcTemplate → JPA → 스프링 데이터 JPA
```

---
## 기술별 비교
| 기술 | SQL | 특징 |
|---|---|---|
| 순수 JDBC | 직접 작성 | Connection, PreparedStatement, ResultSet을 직접 다룸. 반복 코드가 많음 |
| JdbcTemplate | 직접 작성 | 반복 코드를 없애줌. 결과는 RowMapper로 객체에 담음 |
| JPA | **자동 생성** | 객체 중심. `EntityManager`로 저장, 조회. 트랜잭션 필수 |
| 스프링 데이터 JPA | 자동 생성 | 인터페이스만 만들면 구현체 없이 CRUD, 메서드 이름 쿼리, 페이징 |

---
## DataSource (공통)
- DB 연결(Connection)을 얻는 **입구**
- 접속 정보를 `application.properties`에 쓰면 부트가 DataSource를 만들어서 빈으로 등록해둠 → 주입받아서 사용
- 안에 **커넥션 풀**(HikariCP)이 있음
	- 연결을 미리 만들어두고 빌려 쓰고 반납하는 구조
	- 즉 `close()`를 해도 연결이 끊기는게 아니라 풀로 돌아감
- 리포지토리는 접속 정보를 모르고 연결만 빌려 씀 (JPA는 `EntityManager`)

## 구현체 갈아끼우기
- 설정(`SpringConfig`)에서 `@Bean`이 반환하는 구현체 한 줄만 바꿈 → 서비스 코드는 그대로
- 인터페이스로 설계해둔 덕분 (OCP)

---
## JPA
- `@Entity`, `@Id @GeneratedValue`로 테이블 매핑
- 저장 `persist`, 조회 `find`, 조건 조회는 JPQL
```java
em.createQuery("select m from Member m where m.name = :name", Member.class)
	.setParameter("name", name)
	.getResultList();
```
- `:name`은 JDBC의 `?` 대신 쓰는 이름 기반 파라미터 바인딩
- 데이터 변경은 트랜잭션 안에서 → 서비스에 `@Transactional` (정상 종료면 커밋, 런타임 예외면 롤백)

## 통합 테스트
- `@SpringBootTest` + `@Transactional`
- 테스트가 끝나면 **자동 롤백**이라 DB에 데이터가 안 남음

---
## 실무 메모
- JPA + 스프링 데이터 JPA가 기본
- 복잡한 동적 쿼리는 Querydsl, 그래도 어려우면 네이티브 쿼리나 JdbcTemplate
- 스프링 데이터 JPA는 JPA를 편하게 쓰게 해주는거라 **JPA를 먼저** 알아야 함
