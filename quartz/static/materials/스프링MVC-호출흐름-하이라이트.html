스프링 MVC 호출 흐름 (변수 색상 보기)

호출 문장에서 같은 값은 같은 색으로 칠해서, 값이 어디서 만들어져 어디로 흘러가는지 눈으로 따라가는 복습용 문서

호출 순서 색 범례 값의 이동 A 찾기·준비 B 실행 C 마무리 변수 정리표 데이터/화면 차이 전체 코드

호출 순서

카드 하나가 호출 한 번입니다. 왼쪽은 "누가 → 누구를 부르는지", 오른쪽은 실제 호출 문장(돌려받는 값과 넘기는 값)입니다. 1번은 전체를 지휘하는 DispatcherServlet의 순서이고, 2번부터는 각 부품이 자기 안에서 일하는 순서입니다. 번호(예: 3-4)는 "그룹 번호-순서"입니다.

1 DispatcherServlet2 HandlerMapping3 HandlerAdapter4 ArgumentResolver5 ReturnValueHandler6 Converter7 인터셉터 체인8 ViewResolver9 View10 톰캣
1. DispatcherServlet이 부르는 순서 (doDispatch)
1-1
톰캣→ DispatcherServlet
dispatcherServlet.service(req, resp);여기서 doDispatch가 시작됨
1-2
DispatcherServlet→ HandlerMapping
HandlerExecutionChain chain = mapping.getHandler(req);null이면 다음 매핑, 전부 null이면 404
1-3
DispatcherServlet→ HandlerAdapter
boolean ok = adapter.supports(chain.handler());true라고 답한 첫 어댑터를 선택
1-4
DispatcherServlet→ 인터셉터들
boolean go = chain.applyPreHandle(req, resp);앞에서부터 실행, false면 여기서 중단
1-5
DispatcherServlet→ HandlerAdapter
ModelAndView mv = adapter.handle(req, resp, chain.handler());안쪽은 아래 3번 그룹, 데이터 응답이면 mv는 null
1-6
DispatcherServlet→ 인터셉터들
chain.applyPostHandle(req, resp, mv);뒤에서부터 실행
1-7
DispatcherServlet→ ViewResolver
View view = viewResolver.resolveViewName(mv.getViewName());mv가 null이 아닐 때만 (화면 응답)
1-8
DispatcherServlet→ View
view.render(mv.getModel(), req, resp);mv가 null이 아닐 때만, Response에 HTML 기록
1-9
DispatcherServlet→ 인터셉터들
chain.triggerAfterCompletion(req, resp, ex);예외가 나도 실행, 끝나면 톰캣이 HTTP로 전송
2. HandlerMapping 내부 순서 (getHandler 안쪽, 1-2번의 속)
2-1
HandlerMapping→ 주소 뽑기
String path = getLookupPath(req);쿼리를 뺀 주소만 뽑음 (예: /todos/3)
2-2
HandlerMapping→ 매핑 표(registry)
List<Match> candidates = registry.findCandidates(path, req);주소 패턴, HTTP 메서드, 조건이 모두 맞는 후보를 표에서 모음
2-3
HandlerMapping→ DispatcherServlet
if (candidates.isEmpty()) return null;못 찾으면 null을 돌려줘서 DispatcherServlet이 다음 매핑에게 묻게 함
2-4
HandlerMapping→ 후보 비교
Match best = pickMostSpecific(candidates);후보가 여럿이면 가장 구체적인 것 선택 (/todos/me가 /todos/{id}보다 우선)
2-5
HandlerMapping→ req
req.setAttribute("pathVariables", best.pathVariables());{id} 같은 값을 요청에 저장해 둠 (나중에 @PathVariable이 꺼내 씀)
2-6
HandlerMapping→ 인터셉터 선별
List<HandlerInterceptor> interceptors = matchingInterceptors(path);이 주소에 적용되는 인터셉터만 고름
2-7
HandlerMapping→ DispatcherServlet
return new HandlerExecutionChain(best.handlerMethod(), interceptors);핸들러와 인터셉터를 한 묶음으로 반환 (1-2번의 chain이 됨)
3. HandlerAdapter 내부 순서 (adapter.handle() 안쪽, 1-5번의 속)
3-1
HandlerAdapter→ req, resp 묶기
ServletWebRequest web = new ServletWebRequest(req, resp);톰캣이 만든 req, resp를 web 하나로 묶음 (Resolver와 처리기에 한 번에 넘기려고)
3-2
HandlerAdapter→ 보관함 만들기
ModelAndViewContainer mav = new ModelAndViewContainer();요청마다 새 보관함 (Model, 뷰 이름, 응답 완료 표시가 들어 있음)
3-3
HandlerAdapter→ ArgumentResolver
boolean ok = resolver.supports(parameter);매개변수마다 반복, 첫 true를 선택
3-4
HandlerAdapter→ ArgumentResolver
args[i] = resolver.resolveArgument(parameter, mav, web);그 매개변수에 넣을 값을 만들어 args에 저장
3-5
HandlerAdapter→ 내 컨트롤러
Object result = method.invoke(bean, args);컨트롤러 메서드 실행, 반환값이 result에 담김
3-6
HandlerAdapter→ 반환 타입 정보
MethodParameter returnType = handlerMethod.getReturnType();메서드에 선언된 반환 타입과 애너테이션 정보 (실제 반환값 result가 아니라 선언 정보)
3-7
HandlerAdapter→ ReturnValueHandler
boolean ok = returnHandler.supports(returnType);첫 true를 선택 (@ResponseBody 담당인지, 뷰 이름 담당인지)
3-8
HandlerAdapter→ ReturnValueHandler
returnHandler.handleReturnValue(result, returnType, mav, web);데이터면 JSON 기록, 화면이면 뷰 이름을 mav에 저장
3-9
ReturnValueHandler→ HttpMessageConverter
converter.write(value, mediaType, outputMessage);데이터 응답일 때만, Response에 JSON 기록
3-10
HandlerAdapter→ DispatcherServlet
return mav.isRequestHandled() ? null : new ModelAndView(mav.getViewName(), mav.getModel());데이터 응답이면 null, 화면 응답이면 ModelAndView (1-5번의 mv가 됨)
4. ArgumentResolver 내부 순서 (예: @RequestParam 담당, 3-4번의 속)
4-1
ArgumentResolver→ 매개변수 정보
boolean ok = parameter.hasAnnotation(RequestParam.class);supports: 내가 담당할 매개변수인가 (애너테이션과 타입 확인)
4-2
ArgumentResolver→ req
String raw = req.getParameter(parameter.getName());톰캣이 만든 req에서 쿼리 값을 문자열로 꺼냄
4-3
ArgumentResolver→ 매개변수 정보
if (raw == null && parameter.hasDefault()) raw = parameter.getDefaultValue();값이 없으면 defaultValue를 사용
4-4
ArgumentResolver→ 예외
if (raw == null) throw new MissingParameterException(parameter);필수인데 값이 없으면 예외, 400 응답이 됨
4-5
ArgumentResolver→ 타입 변환
Object value = convert(raw, parameter.getType());문자열을 long, int 같은 매개변수 타입으로 변환 (실패하면 400)
4-6
ArgumentResolver→ HandlerAdapter
return value;이 값이 3-4번의 args[i]에 들어감

Model 담당 Resolver는 4-2~4-5 대신 return mav.getModel(); 한 줄로 끝나고, @RequestBody 담당 Resolver는 요청 본문을 읽어 컨버터로 객체를 만듭니다.

5. ReturnValueHandler 내부 순서 (3-8번의 속)

(A) 데이터 응답: @ResponseBody, @RestController 담당

5-1
ReturnValueHandler→ 반환 타입 정보
boolean ok = returnType.hasAnnotation(ResponseBody.class);supports: @ResponseBody(@RestController 포함)가 붙었나
5-2
ReturnValueHandler→ 보관함
mav.setRequestHandled(true);"응답은 내가 끝낸다"고 표시 (그래서 3-10번이 null을 반환)
5-3
ReturnValueHandler→ 컨버터 목록
HttpMessageConverter converter = findConverter(result, mediaType);컨버터들에게 canWrite로 물어 맞는 것을 찾음
5-4
ReturnValueHandler→ resp
HttpOutputMessage outputMessage = wrap(web.getResponse());톰캣의 resp를 쓰기 좋게 감쌈 (web은 req, resp를 묶은 것)
5-5
ReturnValueHandler→ HttpMessageConverter
converter.write(result, mediaType, outputMessage);객체를 JSON으로 만들어 Response에 기록 (다음 6번 그룹)

(B) 화면 응답: 뷰 이름 담당 (위 5-2~5-5 대신 실행)

5-6
ReturnValueHandler→ 반환 타입 정보
boolean ok = returnType.getType() == String.class;supports: 문자열을 반환하는가 (뷰 이름으로 해석)
5-7
ReturnValueHandler→ 보관함
mav.setViewName((String) result);뷰 이름만 저장하고 Response에는 쓰지 않음, 응답 완료 표시도 하지 않음
6. HttpMessageConverter 내부 순서 (Jackson 컨버터, 5-5번의 속)
6-1
컨버터→ 타입, 형식 확인
boolean ok = converter.canWrite(value.getClass(), mediaType);이 타입의 객체를 이 형식(JSON)으로 쓸 수 있나
6-2
컨버터→ 응답 헤더
outputMessage.getHeaders().setContentType("application/json;charset=UTF-8");Content-Type 헤더 설정
6-3
컨버터→ Jackson
byte[] json = objectMapper.writeValueAsBytes(value);객체의 필드 이름과 값을 JSON 바이트로 변환
6-4
컨버터→ Response 출력 스트림
outputMessage.getBody().write(json);JSON 바이트를 Response에 기록 (톰캣이 나중에 HTTP로 전송)
7. HandlerExecutionChain 내부 순서 (인터셉터 호출, 1-4 · 1-6 · 1-9번의 속)
7-1
HandlerExecutionChain→ 인터셉터 (앞에서부터)
boolean go = interceptors.get(i).preHandle(req, resp, handlerMethod);applyPreHandle: 앞에서부터 차례로 실행
7-2
HandlerExecutionChain→ 마무리 호출
if (!go) { triggerAfterCompletion(req, resp, null); return false; }하나라도 false면 이미 실행한 인터셉터들의 마무리만 하고 멈춤
7-3
HandlerExecutionChain→ 인터셉터 (뒤에서부터)
interceptors.get(i).postHandle(req, resp, handlerMethod, mv);applyPostHandle: 뒤에서부터 차례로 실행
7-4
HandlerExecutionChain→ 인터셉터 (뒤에서부터)
interceptors.get(i).afterCompletion(req, resp, handlerMethod, ex);triggerAfterCompletion: 뒤에서부터, 성공이든 실패든 실행
8. ViewResolver 내부 순서 (1-7번의 속)
8-1
ViewResolver→ 파일 위치 조립
String templatePath = prefix + viewName + suffix;예: templates/ + hello + .html
8-2
ViewResolver→ View 만들기
View view = new TemplateView(templatePath);파일을 읽는 일은 render 때 하고, 여기서는 위치만 담은 View를 만듦
8-3
ViewResolver→ DispatcherServlet
return view;못 찾으면 null을 돌려줘서 다음 ViewResolver에게 넘어감
9. View 내부 순서 (render, 1-8번의 속)
9-1
View→ 템플릿 파일
String html = readTemplate(templatePath);templates/hello.html 파일을 읽음
9-2
View→ Model
html = html.replace("${" + key + "}", String.valueOf(model.get(key)));Model의 이름과 값으로 ${이름} 빈칸을 채움 (모든 key에 대해 반복)
9-3
View→ resp
resp.setContentType("text/html;charset=UTF-8");응답 형식 설정
9-4
View→ resp
resp.getWriter().write(html);완성된 HTML을 Response에 기록 (끝나면 render가 반환됨)
10. 톰캣 내부 순서 (1번 그룹을 감싸는 앞뒤)
10-1
톰캣 (Connector)→ 소켓
Socket socket = serverSocket.accept();연결을 받음 (요청 하나를 스레드 하나가 맡음)
10-2
톰캣 (Connector)→ 요청 객체
Request req = parse(socket.getInputStream());HTTP 글자를 해석해 요청 객체를 만듦
10-3
톰캣 (Connector)→ 응답 객체
Response resp = new Response(socket.getOutputStream());비어 있는 응답 객체를 만듦
10-4
서블릿 컨테이너→ 서블릿 선택
Servlet target = pickByUrlPattern(req.getPath());URL 패턴으로 서블릿 선택 (보통 / 패턴의 DispatcherServlet)
10-5
서블릿 컨테이너→ 필터 → DispatcherServlet
new FilterChain(filters, target).doFilter(req, resp);필터들을 거쳐 target.service(req, resp)를 호출 → 1-1번이 시작됨
10-6
톰캣 (Connector)→ 소켓
resp.flush();service()가 끝나면 resp를 HTTP 글자로 바꿔 소켓으로 전송
읽는 요령 같은 색의 이름은 같은 값입니다. 예를 들어 1-5번에서 돌아온 mv(빨강)가 1-6, 1-7, 1-8번에서 계속 쓰이고, 3-10번의 반환이 바로 그 mv가 됩니다. 마찬가지로 4-6번의 value는 3-4번의 args[i]로 이어지고, 2-7번의 반환은 1-2번의 chain이 됩니다. 이렇게 그룹의 마지막 반환이 다른 그룹의 변수로 이어진다는 점을 따라가며 보세요.

값의 이동 한눈에

색이 바뀌는 곳이 "새 값이 만들어지는 곳"입니다.

req→ getHandler → chain→ handler() → handlerMethod→ handle → args→ invoke → result→ handleReturnValue → mav→ 반환 → mv→ resolveViewName → view→ render → Response에 HTML
A

핸들러 찾기와 준비

DispatcherServlet.doDispatch 안 · 어댑터를 부르기 전까지

// ① 핸들러 찾기 (매핑마다 반복)
HandlerExecutionChain chain = mapping.getHandler(req);     // null이면 다음 매핑, 전부 null이면 404

// ② 어댑터 고르기 (어댑터마다 반복)
boolean ok = adapter.supports(chain.handler());            // true라고 답한 첫 어댑터를 선택

// ③ 실행 전 인터셉터
boolean go = chain.applyPreHandle(req, resp);              // false면 여기서 중단
색으로 보기 req가 들어가 chain이 만들어지고, chain에서 핸들러를 꺼내(chain.handler()) 어댑터를 고릅니다. 두 번째 줄의 adapter는 "고르는 대상"이고, ok가 true인 것이 선택됩니다.
B

실행

DispatcherServlet이 어댑터를 호출하는 한 줄과, 그 안쪽에서 일어나는 일

DispatcherServlet 쪽

// ④ 어댑터 실행: 핸들러만 넘기고 mv를 돌려받음
ModelAndView mv = adapter.handle(req, resp, chain.handler());

adapter.handle() 안쪽 (넘겨받은 chain.handler()가 handlerMethod)

// 보관함은 요청마다 새로 만듦
ModelAndViewContainer mav = new ModelAndViewContainer();

// ⑤ 매개변수 값 준비 (매개변수마다 반복)
boolean ok = resolver.supports(parameter);                       // 첫 true를 선택
args[i] = resolver.resolveArgument(parameter, mav, web);        // 그 매개변수에 넣을 값

// ⑥ 컨트롤러 메서드 실행
Object result = method.invoke(bean, args);                      // 반환값이 result에 담김

// ⑦ 반환값 처리
boolean ok = returnHandler.supports(returnType);                 // 첫 true를 선택
returnHandler.handleReturnValue(result, returnType, mav, web);  // 데이터: JSON 기록 / 화면: 뷰 이름 저장
converter.write(value, mediaType, outputMessage);               // 데이터 응답일 때만, Response에 JSON 기록

// ⑧ DispatcherServlet에 돌려줌
return mav.isRequestHandled() ? null : new ModelAndView(mav.getViewName(), mav.getModel());      // 데이터 응답이면 null
색으로 보기 안쪽에서 args가 만들어지고 → result가 나오고 → mav에 결과가 담기고 → 마지막에 mv로 포장되어 위쪽 한 줄의 mv로 돌아옵니다. mav는 resolveArgument와 handleReturnValue에 계속 넘겨져서 보관함이 하나의 요청 안에서 공유됩니다.
이름 주의 안쪽의 returnHandler는 "반환값 처리 담당"이고, 바깥의 chain.handler()는 "실행할 컨트롤러 메서드"입니다. 둘 다 handler라는 말이 들어가서 헷갈리기 쉬워 일부러 이름을 나눴습니다.
C

마무리

어댑터에서 돌아온 뒤 · 응답이 나가기 전까지

// ⑨ 실행 후 인터셉터
chain.applyPostHandle(req, resp, mv);                            // 뒤에서부터 실행

// ⑩ 화면 응답일 때만 (mv가 null이 아닐 때)
View view = viewResolver.resolveViewName(mv.getViewName());     // 뷰 이름으로 View 찾기
view.render(mv.getModel(), req, resp);                           // Model 값으로 HTML을 만들어 Response에 기록

// ⑪ 마무리 인터셉터 (예외가 나도 실행)
chain.triggerAfterCompletion(req, resp, ex);

// 이후 톰캣이 resp를 HTTP 글자로 바꿔 소켓으로 전송
색으로 보기 mv가 view를 찾는 데(뷰 이름)와 렌더링하는 데(Model) 두 번 쓰입니다. 데이터 응답이면 mv가 null이라서 ⑩은 통째로 건너뜁니다.

mv뷰 이름 + Model (또는 null)adapter.handle의 반환applyPostHandle, resolveViewName, render
view찾은 View 객체resolveViewName의 반환view.render

데이터 응답과 화면 응답: 달라지는 줄만

같은 코드에서 갈라지는 부분만 나란히 봅니다.

데이터 응답 (@RestController) 
returnHandler.handleReturnValue(result, returnType, mav, web);  // 컨버터로 JSON을 Response에 기록
// handled = true 로 표시됨

return mav.isRequestHandled() ? null : new ModelAndView(mav.getViewName(), mav.getModel());      // null 반환
// → mv == null

chain.applyPostHandle(req, resp, mv);
// mv가 null이므로 resolveViewName, render는 실행되지 않음
chain.triggerAfterCompletion(req, resp, ex);
화면 응답 (@Controller + 뷰 이름) 
returnHandler.handleReturnValue(result, returnType, mav, web);  // 뷰 이름을 mav.viewName에 저장만 함
// handled = false 그대로

return mav.isRequestHandled() ? null : new ModelAndView(mav.getViewName(), mav.getModel());      // ModelAndView 반환
// → mv = (뷰 이름, Model)

chain.applyPostHandle(req, resp, mv);
View view = viewResolver.resolveViewName(mv.getViewName());
view.render(mv.getModel(), req, resp);                           // HTML을 Response에 기록
chain.triggerAfterCompletion(req, resp, ex);

전체 코드 모아보기

복사해서 두고 볼 수 있게 한 곳에 묶었습니다.

펼쳐서 전체 보기 
// ===== DispatcherServlet.doDispatch (요약) =====
HandlerExecutionChain chain = mapping.getHandler(req);
boolean ok = adapter.supports(chain.handler());

ModelAndView mv = adapter.handle(req, resp, chain.handler());
chain.applyPostHandle(req, resp, mv);

// ===== adapter.handle 안쪽 =====
ModelAndViewContainer mav = new ModelAndViewContainer();

converter.write(value, mediaType, outputMessage);              // 데이터 응답일 때만

코드는 이해를 돕기 위해 줄이고 이름을 단순화한 것이며 실제 스프링 소스가 아닙니다. 실제로는 web이 ServletWebRequest, mav가 ModelAndViewContainer이고, 반환 타입과 메서드 이름이 조금 다릅니다. 정확한 동작은 DispatcherServlet.doDispatch에 중단점을 걸고 확인하세요.
